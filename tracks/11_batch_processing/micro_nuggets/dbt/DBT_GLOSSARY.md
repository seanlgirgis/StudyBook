# dbt Glossary — Plain-English Definitions

Every dbt term defined simply, with a pointer to where it appears in this lane.

---

## Core Macros and Functions

**ref('model_name')**
Generates the correct schema-qualified table name for a dbt model at runtime.
Also registers a DAG dependency so dbt runs the referenced model first.
Use ref() everywhere except the staging layer.
_Shown in: every model in `lab_dbt_project/models/`_

**source('source_name', 'table_name')**
References a raw/external table NOT owned by the dbt project.
Generates the schema-qualified table name from the sources: block in schema.yml.
Enables source freshness checks. Use ONLY in the staging layer.
_Shown in: `models/staging/stg_*.sql`, `models/staging/schema.yml`_

**this**
A Jinja variable that refers to the current model's own fully-qualified table name.
Used in incremental models: `WHERE event_ts > (SELECT max(event_ts) FROM {{ this }})`.
_Shown in: `models/marts/fct_events_incremental.sql`_

## Materializations

**materialization**
How dbt writes a model's results to the database. Defined in dbt_project.yml or the model's config() block. Four types: view, table, incremental, ephemeral.
_Shown in: `lab_dbt_project/dbt_project.yml`, all model files_

**view**
The model SQL is stored as a database view definition. No data is stored — the SELECT runs every time a downstream model queries it. Cheapest to build, slowest to query at scale.
_Shown in: `models/staging/stg_*.sql` (default for staging layer)_

**table**
dbt runs a DROP + CREATE TABLE AS SELECT. All rows are recomputed from scratch each run. Fast to query, predictable, but expensive for large data.
_Shown in: `models/marts/dim_customers.sql`, `models/silver/slv_orders_cleaned.sql`_

**incremental**
dbt only inserts/upserts rows that are NEW or CHANGED since the last run. Controlled by the `{% if is_incremental() %}` block. Requires a `unique_key` for upserts. Huge cost saving for large append-only tables (events, logs).
_Shown in: `models/marts/fct_events_incremental.sql`_

**ephemeral**
The model is NOT materialized in the database at all. Its SQL is inlined as a CTE (Common Table Expression) inside every model that ref()s it. Use for single-consumer intermediate logic.
_Shown in: `models/intermediate/int_orders_with_customers.sql`_

## Snapshot / SCD

**snapshot**
A dbt object (defined in snapshots/ directory) that implements SCD Type 2 automatically. Tracks historical changes to dimension records by inserting new rows and closing old ones with dbt_valid_to timestamps.
_Shown in: `snapshots/customers_snapshot.sql`, nugget `04_snapshots_and_scd/01_snapshots_scd2.py`_

**SCD Type 2 (Slowly Changing Dimension Type 2)**
A data warehousing pattern for tracking dimension history. When a record changes, a new row is inserted with the new values, and the old row's "valid_to" timestamp is set. dbt_valid_to IS NULL = the current active version.
_Shown in: `snapshots/customers_snapshot.sql`_

**dbt_valid_from / dbt_valid_to**
Columns automatically added by dbt to snapshot tables. dbt_valid_from = when this version of the record became active. dbt_valid_to = when it ended (NULL means it's the current version).
_Shown in: `snapshots/customers_snapshot.sql`, nugget `04_snapshots_and_scd/01_snapshots_scd2.py`_

## Configuration Files

**schema.yml**
A YAML file in the models/ directory defining model/source metadata: descriptions, column names, and tests. Acts as the data contract for your models. Can live at any level of the models/ folder hierarchy.
_Shown in: `models/staging/schema.yml`, `models/marts/schema.yml`_

**dbt_project.yml**
The root configuration file for a dbt project. Defines the project name, profile, model/seed/test/snapshot paths, and per-folder materialization defaults and tags. Committed to git. Never contains credentials.
_Shown in: `lab_dbt_project/dbt_project.yml`_

**profiles.yml**
Contains database connection credentials for each target (dev, prod, staging). Lives at `~/.dbt/profiles.yml` by convention — NEVER committed to git. In this lane, auto-generated inside lab_dbt_project/ by `_dbt_lane_connect.py`.
_Shown in: generated by `_dbt_lane_connect.py`, template at `lab_dbt_project/profiles_template.yml`_

## Macros and Jinja

**macro**
A reusable Jinja2 function defined in the macros/ directory. Called with `{{ macro_name(args) }}` inside any model, test, or other macro. Built-in macros: ref(), source(), this, is_incremental(), config().
_Shown in: `macros/cents_to_dollars.sql`, `macros/generate_surrogate_key.sql`_

**Jinja**
The Python-based templating language dbt uses to make SQL dynamic. Allows variables (`{{ var }}`), control flow (`{% if %}`), and macro calls. dbt compiles Jinja → raw SQL before executing.
_Shown in: all model files with `{{ ref() }}`, `{% if is_incremental() %}`_

**compilation**
The step where dbt renders Jinja templates into plain SQL. Happens automatically before execution. Run `dbt compile` to see compiled SQL without executing it. Compiled SQL lives in `target/compiled/`.
_Shown in: nuggets `01_dbt_basics/02_sources_and_staging.py`, `02_modeling.../02_ephemeral_and_ref_graph.py`_

## Artifacts

**manifest.json**
A JSON file generated by every dbt compile/run/test/build/docs command. Contains every node (model, test, seed, snapshot, macro) with compiled SQL, configuration, tags, and DAG dependencies. The foundation for all dbt tooling (Lightdash, elementary, re_data, etc.) and for CI/CD state comparison.
_Shown in: `target/manifest.json`, nugget `05_operations_and_deploy/01_run_build_seed_docs.py`_

**run_results.json**
A JSON file written after every dbt command. Contains per-node execution results: status (pass/fail/error), timing, rows affected. Use this for CI/CD alerting and observability dashboards. Re-written on every run.
_Shown in: `target/run_results.json`, nugget `05_operations_and_deploy/01_run_build_seed_docs.py`_

**catalog.json**
Generated ONLY by `dbt docs generate`. Contains database introspection: column names, data types, row counts for every node. Used by the dbt docs UI for column-level lineage.
_Shown in: `target/catalog.json`, nugget `05_operations_and_deploy/01_run_build_seed_docs.py`_

## Selectors and Graph Operators

**selector**
A filter expression passed to `--select` flag that determines WHICH nodes dbt operates on. Types: model name, tag:name, source:name, path/to/folder, state:modified.
_Shown in: nugget `05_operations_and_deploy/02_selectors_state_artifacts.py`_

**graph operator (+)**
Prepend `+` to include upstream ancestors; append `+` to include downstream descendants. `+model` = model + everything it depends on. `model+` = model + everything that depends on it. `+model+` = full lineage.
_Shown in: nugget `05_operations_and_deploy/02_selectors_state_artifacts.py`_

**@ operator**
Selects a node, all its descendants (downstream), and ALL parents of those descendants. More inclusive than `+`. Used for "I want this node and everything connected around it."
_Shown in: nugget `05_operations_and_deploy/02_selectors_state_artifacts.py`_

**tag: selector**
Select all nodes with a specific tag. Tags are defined in dbt_project.yml or model config() blocks. Example: `dbt run --select tag:daily`.
_Shown in: `lab_dbt_project/dbt_project.yml` (tags: daily, mart, hourly), nuggets_

**source: selector**
Select nodes relative to a source. `source:dbt_lab_raw+` = all models downstream of the dbt_lab_raw source.
_Shown in: nugget `05_operations_and_deploy/02_selectors_state_artifacts.py`_

**state:modified**
Compares current manifest.json to a previous one and selects only nodes whose SQL or config changed. The CI/CD "smart rebuild" pattern: only run what changed + downstream.
_Shown in: nugget `05_operations_and_deploy/02_selectors_state_artifacts.py`_

## Seeds and Tests

**seed**
A CSV file in the seeds/ directory that dbt loads into the database as a table via `dbt seed`. Good for small reference data (country codes, tier mappings) and test data. Not for large datasets.
_Shown in: `lab_dbt_project/seeds/`, nugget `00_setup/01_seed_lab.py`_

**generic test**
A parameterized test defined in schema.yml using built-in keywords (not_null, unique, relationships, accepted_values). dbt auto-generates SQL for each. Apply to any column in any model with a one-liner.
_Shown in: `models/staging/schema.yml`, nugget `03_tests_and_quality/01_generic_tests.py`_

**singular test**
A raw SQL file in the tests/ directory. Must return 0 rows to pass. Use for complex business-logic assertions that generic tests can't express. Uses ref() for environment portability.
_Shown in: `tests/assert_positive_amounts.sql`, `tests/assert_no_future_dates.sql`, nugget `03_tests_and_quality/02_custom_tests...`_

**data contract**
The schema.yml file as a formal agreement between a model's author and its consumers. Specifies column names, descriptions, types, and test expectations. Makes implicit assumptions explicit and machine-checkable.
_Shown in: `models/staging/schema.yml`, `models/marts/schema.yml`_

## Operations

**defer**
A flag (`--defer --state ./prod_manifest/`) that tells dbt to use PRODUCTION schema objects for unchanged upstream models during development. Only rebuild the model you're working on. Requires prod manifest.json.
_Shown in: nugget `05_operations_and_deploy/02_selectors_state_artifacts.py`_

**dbt build vs dbt run vs dbt test**
`dbt run` executes model SQL only. `dbt test` runs tests only. `dbt build` = run + test + seed + snapshot in DAG order, testing each node before running its downstream dependents. Use `dbt build` in CI/CD.
_Shown in: nugget `05_operations_and_deploy/01_run_build_seed_docs.py`_

**DAG (Directed Acyclic Graph)**
The execution dependency graph built from ref() and source() calls. Directed = one-way dependency. Acyclic = no circular dependencies. dbt sorts the DAG topologically to determine execution order.
_Shown in: nugget `02_modeling_and_materializations/02_ephemeral_and_ref_graph.py`_

**lineage**
The end-to-end dependency chain from raw sources to final gold/mart tables. "What does stg_customers feed into?" and "Where did this gold table's data come from?" dbt docs visualizes lineage from the manifest.
_Shown in: nugget `07_mini_capstone/01_mini_capstone.py`, dbt docs UI_

**dependency**
A model A "depends on" model B when A's SQL contains `ref('B')`. dbt ensures B is built before A. Dependencies form the DAG edges.
_Shown in: all model files using ref()_
