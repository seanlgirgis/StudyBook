### Section content to generate:

**s1 — What IAM Is**
- IAM is the permission system for all of AWS — evaluates every API call across every service
- Three questions it answers: authentication (who are you?), authorization (are you allowed?)
- Global service — not region-scoped. One IAM configuration governs the entire account.
- Default: everything is implicitly denied. You must explicitly grant permissions.
- `.hi`: IAM evaluates on every single API call — no cached "you're logged in" state
- `.warn`: The root account has permanent, irrevocable full access. Enable MFA, create no root access keys, never use it day-to-day.

**s2 — Core Primitives: Users, Groups, Roles, Policies**
- Users: long-term identity — console password or access keys. For humans or legacy programmatic access.
- Groups: collection of users for policy management. Change one group, affects all members.
- Roles: identity without long-term credentials. Issues temporary tokens via STS. For services and applications.
- Policies: JSON documents that define what is allowed or denied. Attached to any of the above.
- `.hi`: Roles are the modern standard for anything non-human. Never give a service an access key.
- Use a table showing: User / Group / Role / Policy — Purpose, Credentials, Lifetime, Best used for

**s3 — Policy Document Anatomy**
- JSON structure: Version, Statement array
- Statement fields: Effect (Allow | Deny), Action (API operations), Resource (ARN), Condition (optional constraints)
- Effect: Deny ALWAYS wins — explicit deny overrides any Allow, from any policy
- Action wildcards: `s3:GetObject` is specific; `s3:*` is all S3 actions; `*` is all AWS actions
- Resource ARN format: `arn:aws:s3:::my-bucket/*` vs `arn:aws:s3:::my-bucket` (bucket vs objects)
- Condition keys: `aws:SourceVpc`, `aws:MultiFactorAuthPresent`, `aws:RequestedRegion`
- Include a `<pre><code>` block showing a well-formed minimal policy example
- `.warn`: Resource `*` with Action `*` and Effect Allow is effectively admin access — never use in production

**s4 — Policy Types and Evaluation Logic**
- Identity-based: attached to a user, group, or role — defines what that identity can do
- Resource-based: attached to the resource itself (S3 bucket policy, SQS queue policy) — defines who can access it
- Permission boundaries: IAM policy that caps the maximum permissions an identity can ever have
- SCPs (Service Control Policies): organizational guardrails applied at the AWS Organizations level — override even admin permissions
- Evaluation order: Organizations SCP → Resource policy → Permission boundary → Identity policy
- `.hi`: An explicit Deny anywhere in the chain ends evaluation immediately — no Allow can override it

**s5 — Roles vs Users: The Critical Distinction**
- Users have static credentials: access keys are permanent until manually rotated
- Roles issue temporary credentials via STS: expire in 15 minutes to 12 hours — bounded blast radius
- The rule: every AWS service gets a role. EC2 → instance profile. Lambda → execution role. ECS task → task role. Glue → service role.
- Why this matters in interviews: "hardcoded credentials on an EC2 instance" is always wrong
- `.hi`: Even if credentials are leaked, STS tokens expire automatically. A leaked access key is valid forever.
- `.warn`: Access keys should not exist for service accounts. If you find them, rotate and delete immediately.

**s6 — How Services Get Permissions**
- EC2 instance profile: IAM role attached at launch — instance metadata service vends temporary credentials automatically — AWS SDK picks them up with no code changes
- Lambda execution role: attached at function creation — must include `logs:CreateLogGroup`, `logs:PutLogEvents` or CloudWatch logging silently fails
- ECS task role vs task execution role:
  - Task execution role: used by the ECS agent — pulls ECR image, writes CloudWatch logs
  - Task role: used by YOUR application code inside the container — what it can call in AWS
  - These are two DIFFERENT roles — confusing them is a very common mistake
- Glue service role: needs S3 read/write, Glue Catalog permissions, and any downstream service (Secrets Manager, KMS)
- `.warn`: The ECS task role and task execution role must be configured separately. Forgetting the task role means your container has zero AWS permissions.

**s7 — AssumeRole and STS**
- AssumeRole: API call to STS that exchanges your current credentials for temporary credentials of a different role
- Returns: AccessKeyId, SecretAccessKey, SessionToken — valid for the session duration you specify
- Use cases: elevate to a sensitive role (with MFA requirement), switch to a cross-account role, CI/CD pipeline authentication
- Session duration: 15 minutes to 12 hours for most roles (up to 12 hours for roles that allow it)
- AWS SDK handles AssumeRole automatically when you configure a profile with `role_arn` — no manual code needed
- `.hi`: AssumeRole is the foundation of all cross-account and federated access patterns in AWS

**s8 — Cross-Account Access**
- Pattern: Role in Account B has a trust policy allowing Account A's role to assume it
- Trust policy names the trusted principal by ARN: the role or account allowed to call AssumeRole
- External ID: optional condition in the trust policy — prevents confused deputy attacks when granting access to third parties
- Common data engineering pattern: central data lake account (Account B) grants specific pipeline accounts (Account A, Account C) assume rights on a role with scoped S3 write access
- Include a trust policy JSON example in a `<pre><code>` block
- `.warn`: The trust policy controls WHO can assume the role. The permission policy controls WHAT the role can do. You need both to be correct.

**s9 — IAM in a Data Engineering Stack**
- Glue crawler: read S3 prefix, write Glue Catalog — nothing else
- Glue ETL job: read source S3, write target S3, Secrets Manager get-secret — scoped to specific resources
- Lambda trigger: read SQS, write to target — minimal surface area
- Redshift Spectrum role: read specific S3 prefixes only — separate from the Redshift cluster role
- EMR service role + EC2 instance profile — two separate roles, both required
- Monitoring: IAM Access Analyzer flags overly permissive policies and cross-account access. CloudTrail logs every IAM change.
- `.hi`: Defense in depth: scope the IAM role AND the S3 bucket policy. Even if a role is over-permissive, the bucket policy is a second enforcement layer.

**s10 — S3 Bucket Policies**
- Resource-based policy attached to the bucket — evaluated in addition to identity policies
- Use cases: grant cross-account access, enforce encryption (deny PutObject without SSE), restrict to specific VPC endpoint
- Key condition: `aws:SourceVpc` — only allow requests from your VPC, blocking public internet access
- Deny HTTP (non-HTTPS) requests: condition `aws:SecureTransport: false` → Effect Deny
- Include a bucket policy example in a `<pre><code>` block: deny all requests not from a specific VPC endpoint
- `.warn`: If both the identity policy and bucket policy must allow access for a same-account request. For cross-account, the bucket policy alone can grant access — but the identity policy in the external account must also allow it.

**s11 — Permission Boundaries**
- An IAM policy that defines the maximum permissions an identity can ever have — even if their attached policies grant more
- Use case: allow developers to create IAM roles for their Lambda functions, but cap what those roles can grant — developers can't create roles with admin access
- The effective permissions = intersection of permission boundary AND identity policy
- Common pattern: every role created by the data team must have the permission boundary attached — enforced via SCP
- `.hi`: Permission boundaries don't grant permissions — they cap them. You still need the identity policy to actually grant access within the boundary.

**s12 — Common Mistakes**
List as a series of `.warn` blocks:
- Hardcoding access keys in application code or `.env` files — attach a role instead
- Star-star policies (`Action: *`, `Resource: *`) — effectively root access, never acceptable in production
- Confusing ECS task role and task execution role — diagnose by checking CloudWatch logs are missing vs AWS SDK calls failing
- Not setting `DeleteOnTermination: false` for data EBS volumes (IAM-adjacent ops mistake)
- Forgetting `sts:AssumeRole` permission in the identity policy of the caller — the trust policy allows it but the caller also needs permission to call AssumeRole
- Using the AWS root account for day-to-day operations
- Access keys that are never rotated — use IAM Access Advisor to find keys unused for 90+ days

**s13 — Least Privilege in Practice**
- Start with AWS-managed policies during development, then use IAM Access Analyzer to generate a least-privilege policy based on actual CloudTrail usage
- Policy simulator: test a policy against specific actions before deploying
- IAM Access Advisor (per role): shows last accessed time for each service — remove unused permissions
- Naming conventions: role names should encode the service and environment — `glue-etl-prod`, `lambda-trigger-dev`
- Version control your IAM policies in Terraform or CloudFormation — reviewable, auditable, reproducible
- `.hi`: AWS IAM Access Analyzer can auto-generate a minimal policy from CloudTrail logs. Use it after a job has been running for a few weeks.
