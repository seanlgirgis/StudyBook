13. UDF and pandas UDF

Prefer built-ins first. Use UDF when needed, with performance caution.

UDF Decision Ladder: Built-ins First, UDFs Carefully

UDFs allow custom logic in PySpark, but they can add performance and support cost. The default should be built-in Spark DataFrame or SQL functions whenever possible.

  1. Use built-in Spark DataFrame or SQL functions first.
  2. Use DataFrame expressions for simple arithmetic, string, date, null, and conditional logic.
  3. Use a regular PySpark UDF only when custom logic is not easy with built-ins.
  4. Use a pandas UDF when custom logic is needed and vectorized execution is a better fit.
  5. Treat external/JVM/platform-specific UDFs as environment-specific choices, not the default beginner pattern.
df = df.withColumn("10_plus", df["value"] + 10)
from pyspark.sql.functions import pandas_udf
from pyspark.sql.types import DoubleType

@pandas_udf(DoubleType())
def add_ten_pandas(column):
    return column + 10

df = df.withColumn(
    "10_plus",
    add_ten_pandas(df["value"])
)

df.show()

Plain English: pandas UDF syntax is useful, but simple logic like adding 10 should stay as built-in expression.

Production angle: validate null handling, return type, performance impact, row counts, and whether built-ins can replace UDF logic.

Common mistake: using UDF for logic Spark built-ins already cover.

Interview-safe answer: I use built-ins first, then choose regular UDF or pandas UDF only when custom logic and runtime tradeoffs justify it.

Punch line: Built-in Spark functions first. UDFs only when custom logic is worth the cost.

RDDs vs DataFrames

RDD means Resilient Distributed Dataset. It is Spark's lower-level distributed abstraction. RDDs are immutable, so transformations create new RDDs.

Plain English: RDDs are closer to raw Spark engine behavior. DataFrames are higher-level, schema-aware, and usually better for structured ETL and analytics.

  • parallelization: split data and computation across workers
  • map(): apply function to each element
  • filter(): keep matching elements
  • collect(): bring distributed data back to driver
# Convert a DataFrame to an RDD
rdd = df.rdd

# Apply map to an RDD
mapped_rdd = rdd.map(lambda row: row)

# Filter an RDD
filtered_rdd = rdd.filter(lambda row: row["age"] > 40)

# Collect tiny results only
small_result = filtered_rdd.collect()

Production warning: collect() can overload driver memory on large datasets.

Interview-safe answer: RDDs are foundational and useful for low-level custom processing, but DataFrames are usually preferred for structured ETL because they are schema-aware and easier to optimize.

Punch line: RDDs teach Spark internals; DataFrames are usually the practical structured ETL path.

Spark SQL and Temporary Views

Spark SQL connects SQL-style logic with DataFrame workflows inside one Spark application.

Plain English: register DataFrame as temp view, run spark.sql(), keep processing returned DataFrame.

# Load data into a DataFrame
employees_df = spark.read.csv(
    "employees.csv",
    header=True,
    inferSchema=True
)

# Register as a temporary SQL view
employees_df.createOrReplaceTempView("employees")

# Query with Spark SQL
high_earners = spark.sql("""
    SELECT name, salary
    FROM employees
    WHERE salary > 100000
""")

# SQL result is still a DataFrame
high_earners.show()

Key points: temp view is session-scoped, spark.sql() returns DataFrame, SQL + DataFrame steps can be blended.

Common mistake: thinking temp view is permanent table.

Production angle: validate row counts before/after SQL filters, joins, aggregations; persist final outputs intentionally.

Interview-safe answer: Spark SQL lets SQL skills operate inside scalable PySpark pipelines, with DataFrame continuity end to end.

Punch line: Spark SQL and DataFrames work together in one distributed pipeline.

Spark SQL result can continue as a DataFrame

Concept: spark.sql() returns a DataFrame, so SQL output can continue with DataFrame methods like describe(), filter(), select(), withColumn(), and write.

salaries_df.createOrReplaceTempView("salaries_table")

query = """
    SELECT job_title, salary_in_usd
    FROM salaries_table
    WHERE company_location = 'CA'
"""

canada_titles = spark.sql(query)

canada_titles.describe().show()

Plain English: SQL result is still DataFrame, so DataFrame profiling methods apply.

Common mistake: assuming SQL output is SQL-only object.

SQL style note: prefer = in SQL strings.

Production angle: verify numeric types, filtered row counts, and standardized filter values before trusting describe output.

Punch line: SQL and DataFrame methods chain in one Spark workflow.

PySpark Aggregations Best Practices

Concept: Aggregations can be done via Spark SQL or DataFrame API using SUM, COUNT, AVG, MAX, MIN.

Plain English: Aggregations summarize many rows into business metrics, but only trustworthy after filtering, typing, cleaning, and validation.

df.createOrReplaceTempView("employees")

result = spark.sql("""
    SELECT department,
           SUM(salary) AS total_salary,
           AVG(salary) AS avg_salary,
           COUNT(*) AS employee_count
    FROM employees
    GROUP BY department
    ORDER BY total_salary DESC
""")

result.show()
from pyspark.sql.functions import sum, avg, count, max, min

result = (
    df
    .groupBy("department")
    .agg(
        sum("salary").alias("total_salary"),
        avg("salary").alias("avg_salary"),
        count("*").alias("employee_count"),
        max("salary").alias("max_salary"),
        min("salary").alias("min_salary")
    )
)

result.show()
from pyspark.sql.functions import col

df_clean = df.withColumn(
    "salary",
    col("salary").cast("double")
)

Best practices: filter early, cast numeric types, handle nulls, validate row counts and grouping values, use explain() when performance matters.

RDD note: possible but more verbose for structured analytics than DataFrame/SQL paths.

Common mistake: SUM/AVG on string-typed values or unvalidated filtered input.

Punch line: Aggregate only after data is filtered, typed, cleaned, and validated.

PySpark at Scale: explain(), cache(), persist(), broadcast(), and repeated actions

Concept: At scale, performance depends on execution plan, shuffle behavior, reuse strategy, and action patterns.

Plain English: explain() shows plan, cache/persist avoid recompute, broadcast can reduce join shuffle, repeated actions trigger repeated jobs.

df.explain()
filtered_df = df.filter(df["company_location"] == "US")
filtered_df.cache()
filtered_df.count()
filtered_df.groupBy("job_title").avg("salary_in_usd").show()
filtered_df.unpersist()
from pyspark import StorageLevel

df.persist(StorageLevel.MEMORY_AND_DISK)
df.unpersist()
from pyspark.sql.functions import broadcast

joined_df = large_df.join(
    broadcast(small_lookup_df),
    on="key",
    how="left"
)

Best practices: inspect plan, watch shuffles, filter early, cache/persist only reused intermediates, unpersist when done, avoid repeated actions, consider broadcast for small lookups.

Common mistakes: repeated actions, over-caching, forgetting unpersist, ignoring shuffles, collect() on large data.

Punch line: at scale, ask how Spark executes, shuffles, recomputes, and uses resources.
