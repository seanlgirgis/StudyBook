01

The Big Idea — What is a Window?

A window function calculates across a set of rows related to the current row — but unlike GROUP BY, it does not collapse those rows into one output row. Every original row stays visible. The function just attaches extra context to each one.

Think of it like a sliding pane of glass moving across your result set. The function "looks through the window" at nearby rows and computes something, then stamps that result onto the current row — and moves on.

CORE MENTAL MODEL GROUP BY collapses rows. Window functions keep rows — they only add columns.
// WHAT A WINDOW FUNCTION DOES TO YOUR DATA

2025-01-01E0037002700

2025-01-02E0058103200
2025-01-02E0067403200

Every sale row is preserved. The window function just adds the daily total as a new column — each row can see its own group's aggregate.

// NUGGET Window function = keep all rows + attach group-level context to each row.

02

OVER() — The Magic Clause

The OVER() clause is what turns any function into a window function. Without OVER(), SUM() is a regular aggregate that collapses rows. With OVER(), it becomes a window calculation that keeps rows.

SUM(revenue) OVER ( ← OVER() turns this into a window function PARTITION BY sale_date ← define the buckets (optional) ORDER BY revenue DESC ← sort within each bucket (optional) ROWS BETWEEN UNBOUNDED PRECEDING ← frame boundaries (optional) AND CURRENT ROW )

All three clauses inside OVER() are optional. An empty OVER() means: apply across the entire result set.

WITHOUT OVER → aggregate
SELECT
  sale_date,
  SUM(revenue) AS total
FROM sales
GROUP BY sale_date;
-- One row per date. Detail gone.
WITH OVER → window
SELECT
  sale_date, event_id, revenue,
  SUM(revenue) OVER (
    PARTITION BY sale_date
  ) AS total
FROM sales;
-- All rows kept. Total attached.
// NUGGET OVER() is the switch. It says: "don't collapse — slide a window instead."

03

GROUP BY vs PARTITION BY

These two look similar but they have fundamentally different output shapes.

GROUP BY — collapses
SELECT
  sale_date,
  SUM(revenue) AS daily_rev
FROM sales
GROUP BY sale_date;
PARTITION BY — keeps all rows
SELECT
  sale_date, event_id, revenue,
  SUM(revenue) OVER (
    PARTITION BY sale_date
  ) AS daily_rev
FROM sales;
// OUTPUT SHAPE COMPARISON
ApproachOutput rowsevent_id visible?revenue visible?
GROUP BY sale_date1 per dateNo — goneNo — gone
PARTITION BY sale_dateAll original rowsYesYes
KEY INSIGHT PARTITION BY is the windowing equivalent of GROUP BY — it defines the "group" for the calculation. But it never removes rows from your output.

What happens without PARTITION BY? The window spans the entire result set. One giant bucket. Example: SUM(revenue) OVER () gives the grand total on every row.

// NUGGET PARTITION BY is bucketing without collapsing.
GROUP BY is bucketing that collapses.
That is the entire difference.

ORDER BY Inside OVER — Two Jobs, One Keyword

There are two places you can write ORDER BY in a window query. They do completely different things and beginners constantly mix them up.

ORDER BY inside OVER()
ROW_NUMBER() OVER (
  ORDER BY revenue DESC
)
ORDER BY at end of query
FROM sales
ORDER BY sale_date;
// WHO DOES WHAT
LocationControlsEffect
ORDER BY inside OVER()Calculation orderHow the window function counts/sums/ranks
ORDER BY at end of SELECTDisplay orderHow rows appear on screen — has zero effect on window calc
 
SELECT
    region, sale_date, revenue,
    NTILE(4) OVER (
        PARTITION BY region
        ORDER BY revenue DESC  -- ← CALCULATION: quartile is built by revenue rank
    ) AS quartile
FROM sales
ORDER BY sale_date;           -- ← DISPLAY: rows show up sorted by date

The quartile was calculated by revenue order. But the screen shows rows sorted by date. Those are independent operations.

// NUGGET ORDER BY inside OVER = "how to calculate".
ORDER BY at the end = "how to display".
They never interfere with each other.

05

ROW_NUMBER() — Unique Position for Every Row

ROW_NUMBER() assigns a unique sequential integer to each row within the window. It never produces ties — if two rows look identical to the sort, it picks an arbitrary but stable winner.

SELECT
    sale_date, event_id, revenue,
    ROW_NUMBER() OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC, event_id  -- tie breaker!
    ) AS row_num_inside_day
FROM sales
ORDER BY sale_date, row_num_inside_day;
// RESULT: numbering resets per sale_date partition
sale_dateevent_idrevenuerow_num_inside_day
2025-01-01E0019001
2025-01-01E0027002
2025-01-01E0037003
2025-01-01E0044004
2025-01-02E0058101
2025-01-02E0067402
TIE BREAKER RULE For ROW_NUMBER, always add a unique column (like event_id) as a secondary sort key. Without it, tied revenue values get arbitrary ordering — your results become non-deterministic.

Classic use case: Get the single top earner per day (de-duplication pattern):

WITH ranked AS (
    SELECT *,
        ROW_NUMBER() OVER (
            PARTITION BY sale_date
            ORDER BY revenue DESC, event_id
        ) AS rn
    FROM sales
)
SELECT * FROM ranked WHERE rn = 1;
// NUGGET ROW_NUMBER never ties. If you need the #1 per group, ROW_NUMBER + CTE + WHERE rn = 1 is the pattern.

RANK() — Ties Get Same Rank, Gaps Happen

RANK() handles ties by giving them the same rank number. But it then skips the next rank — leaving a gap.

Think of the Olympics: two silver medalists means there's no bronze.

SELECT
    sale_date, event_id, revenue,
    RANK() OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC
        -- DO NOT add event_id here — that breaks the tie
    ) AS rank_num
FROM sales
WHERE sale_date = '2025-01-01';
// revenues: 900, 700, 700, 400
revenueRANK()note
9001🥇 Gold
7002🥈 Silver
7002🥈 Silver (tie)
4004← rank 3 is skipped
// NUGGET RANK() = medals. Two silvers means no bronze. Gaps are intentional — they represent the "missing" positions.

07

DENSE_RANK() — Ties Get Same Rank, No Gaps

DENSE_RANK() is like RANK() — ties share the same number — but it never leaves gaps. The next distinct value always gets the next consecutive rank.

Same Olympics scenario, but now bronze gets assigned even after two silvers.

SELECT
    sale_date, event_id, revenue,
    DENSE_RANK() OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC
    ) AS dense_rank_num
FROM sales
WHERE sale_date = '2025-01-01';
// revenues: 900, 700, 700, 400
revenueDENSE_RANK()note
9001🥇 Gold
7002🥈 Silver
7002🥈 Silver (tie)
4003🥉 Bronze — no gap!
WHEN TO USE WHICH Use RANK() when gaps matter semantically (e.g. leaderboard positions). Use DENSE_RANK() when you want "how many distinct tiers above this row" — like pricing tiers, loyalty levels, or product categories.
// NUGGET DENSE_RANK = the count of distinct better values above you. That's it. No gaps, ever.

LAG() — Look at the Previous Row

LAG() fetches a value from a previous row in the window. The default offset is 1 (one row back). The first row in each partition gets NULL because there's nothing before it.

LAG(column)         OVER (...)   -- default: 1 row back
LAG(column, 2)      OVER (...)   -- 2 rows back
LAG(column, 1, 0)   OVER (...)   -- 1 row back, default 0 if NULL
SELECT
    sale_date, event_id, revenue,
    LAG(revenue) OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC, event_id
    ) AS previous_revenue
FROM sales
WHERE sale_date = '2025-01-01';
// LAG RESULT — revenues: 900, 700, 700, 400
revenueprevious_revenue (LAG)
900NULL ← nothing before it
700900
700700
400700
// NUGGET LAG brings a value from behind. First row always gets NULL — there's no "behind" for it.

LEAD() — Look at the Next Row

LEAD() is the forward mirror of LAG(). It fetches a value from a future row in the window. The last row gets NULL.

SELECT
    sale_date, event_id, revenue,
    LEAD(revenue) OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC, event_id
    ) AS next_revenue
FROM sales
WHERE sale_date = '2025-01-01';
// LEAD RESULT — revenues: 900, 700, 700, 400
revenuenext_revenue (LEAD)
900700
700700
700400
400NULL ← nothing after it
LAG — backward
LAG(col) OVER (...)
-- Current row looks BACK
-- First row = NULL
LEAD — forward
LEAD(col) OVER (...)
-- Current row looks FORWARD
-- Last row = NULL
// NUGGET LAG = rearview mirror. LEAD = windshield. One looks back, one looks forward.

11

LAG/LEAD with CTE — The Percent Change Pattern

You can't reference a window function alias inside the same SELECT. So the pattern is: compute LAG in a CTE, then use that column in the outer query for further math.

WITH revenue_with_lag AS (
    SELECT
        sale_date, event_id, revenue,
        LAG(revenue) OVER (
            PARTITION BY sale_date
            ORDER BY revenue DESC, event_id
        ) AS previous_revenue
    FROM sales
    WHERE sale_date = '2025-01-01'
)

SELECT
    sale_date, event_id, revenue,
    previous_revenue,
    ROUND(
        100.0 * (revenue - previous_revenue)
            / NULLIF(previous_revenue, 0),
        2
    ) AS pct_change
FROM revenue_with_lag
ORDER BY revenue DESC, event_id;
WHY CTE IS NECESSARY HERE You cannot write ... / NULLIF(previous_revenue, 0) in the same SELECT that defines previous_revenue. SQL evaluates all SELECT expressions in parallel — column aliases aren't visible to other columns in the same SELECT. The CTE materializes the result first, then the outer query can reference it.
// NUGGET CTE → compute LAG once. Outer query → reuse the result. Never try to reference a window alias in the same SELECT.

12

FIRST_VALUE() / LAST_VALUE() — Boundary Anchors

These functions grab the first or last value of a column within the window frame. Useful for "distance from the leader" or "how far from the bottom" calculations.

SELECT
    sale_date, event_id, revenue,

    FIRST_VALUE(revenue) OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC
    ) AS max_rev_that_day,   -- first in DESC = highest

    LAST_VALUE(revenue) OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC
        ROWS BETWEEN UNBOUNDED PRECEDING
             AND UNBOUNDED FOLLOWING   -- CRITICAL for LAST_VALUE!
    ) AS min_rev_that_day
FROM sales;
LAST_VALUE GOTCHA — the default frame LAST_VALUE with the default frame (RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) only looks back to the current row — so it returns the current row's own value for most rows. Always add ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING to see the true last value in the partition.
// NUGGET FIRST_VALUE is safe by default. LAST_VALUE needs an explicit full-range frame — otherwise it lies.

Aggregate Window Functions — SUM, AVG, MIN, MAX, COUNT

Every standard aggregate function can become a window function by adding OVER(). The behavior changes based on whether you include ORDER BY inside the window.

No ORDER BY → full group total
SUM(revenue) OVER (
  PARTITION BY sale_date
)
-- Every row in the same day
-- gets the SAME total (2700)
With ORDER BY → running total
SUM(revenue) OVER (
  PARTITION BY sale_date
  ORDER BY revenue DESC
)
-- Each row gets cumulative
-- sum up to that row

All five aggregates follow the same pattern:

// AGGREGATE WINDOW FUNCTION BEHAVIOR
FunctionWithout ORDER BYWith ORDER BY
SUM()Group total (same for all rows)Running total
AVG()Group averageRunning average
MIN()Group minimumRunning minimum
MAX()Group maximumRunning maximum
COUNT()Group countRunning count
// NUGGET Same function — completely different meaning depending on whether ORDER BY is present inside OVER(). ORDER BY is the switch between "snapshot" and "running" mode.

Running Totals

A running total accumulates: each row = its own value + all previous row values in the ordered window. This is the canonical use of SUM() OVER(ORDER BY ...).

SELECT
    sale_date, event_id, revenue,
    SUM(revenue) OVER (
        PARTITION BY sale_date
        ORDER BY revenue DESC, event_id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_revenue
FROM sales
WHERE sale_date = '2025-01-01'
ORDER BY revenue DESC, event_id;
// RUNNING TOTAL — visualized
row 1900→ running: 900
row 2700→ running: 1600
row 3700→ running: 2300
row 4400→ running: 2700 ← full total
// NUGGET Running total = all rows from the start of the partition through the current row. The last row's running total always equals the group total.

Moving Averages

A moving average smooths noisy data by averaging over a sliding window of N rows. Unlike running totals (which always look back to the beginning), moving averages look back only N rows.

-- 3-row moving average (current row + 2 preceding)
SELECT
    sale_date, event_id, revenue,
    ROUND(
        AVG(revenue) OVER (
            PARTITION BY sale_date
            ORDER BY revenue DESC, event_id
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ),
        2
    ) AS moving_avg_3
FROM sales;
// SLIDING WINDOW for revenues: 900, 700, 700, 400
rowrevenuewindow includesmoving_avg_3
1900[900]900.00
2700[900, 700]800.00
3700[900, 700, 700]766.67
4400[700, 700, 400] ← slides, drops 900600.00

Two-level pattern: compute daily averages first, then moving average over those daily numbers — a real telemetry/BI pattern.

WITH daily_revenue AS (
    SELECT
        sale_date,
        AVG(revenue) AS avg_revenue_that_day
    FROM sales
    GROUP BY sale_date
)
SELECT
    sale_date,
    ROUND(avg_revenue_that_day, 2) AS avg_daily,
    ROUND(
        AVG(avg_revenue_that_day) OVER (
            ORDER BY sale_date
            ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
        ),
        2
    ) AS moving_avg_3_days
FROM daily_revenue
ORDER BY sale_date;
// NUGGET Running total = frame starts at the beginning. Moving average = frame slides with you. The frame clause is the only difference.

Percent of Total

A window function lets each row compare itself to its own group total — without a separate subquery or join.

SELECT
    sale_date, event_id, revenue,

    SUM(revenue) OVER (
        PARTITION BY sale_date
    ) AS total_rev_that_day,

    ROUND(
        100.0 * revenue
            / SUM(revenue) OVER (PARTITION BY sale_date),
        2
    ) AS pct_of_day_revenue

FROM sales
ORDER BY sale_date, revenue DESC;

Change what you partition by to change the reference group:

// PARTITION BY IS THE DENOMINATOR
PARTITION BYPercent of ...
sale_datethat day's total
regionthat region's total
salespersonthat salesperson's total
product_categorythat category's total
(no partition)grand total of everything
// NUGGET Change the PARTITION BY, change the denominator. The formula stays exactly the same.

ROWS vs RANGE — Frame Modes

The frame clause has two modes: ROWS and RANGE. They look similar but behave differently with ties.

ROWS mode
ROWS BETWEEN 2 PRECEDING
    AND CURRENT ROW
-- Physical row count.
-- "the 2 rows before this one"
-- Exact, deterministic.
RANGE mode
RANGE BETWEEN UNBOUNDED PRECEDING
    AND CURRENT ROW
-- Logical value range.
-- Includes ALL rows with
-- same ORDER BY value.
DEFAULT FRAME TRAP When you write ORDER BY inside OVER() but no frame clause, PostgreSQL defaults to: RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. This means tied values are all included in the frame. Use explicit ROWS BETWEEN for predictable behavior.
// ROWS vs RANGE with duplicate values
revenueROWS mode resultRANGE mode result
900900900
70016002300 ← includes both 700s
70023002300
40027002700
// NUGGET ROWS = physical positions. RANGE = logical value boundaries. For running totals and moving averages, always use ROWS — it's precise and predictable.

Frame Boundaries — The Full Map

The BETWEEN ... AND ... clause inside the frame has five boundary keywords:

// FRAME BOUNDARY KEYWORDS
BoundaryMeaning
UNBOUNDED PRECEDINGFirst row of the partition — the very beginning
N PRECEDINGN rows before the current row
CURRENT ROWThe current row itself
N FOLLOWINGN rows after the current row
UNBOUNDED FOLLOWINGLast row of the partition — the very end

Common frame combinations and what they produce:

-- Running total (beginning to here)
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW

-- Full group total (entire partition)
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING

-- 3-row moving average (centered)
ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING

-- Current row only
ROWS BETWEEN CURRENT ROW AND CURRENT ROW

-- Trailing 7-day window
ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
// NUGGET The frame clause is a range dial: UNBOUNDED = whole partition, N = sliding window, CURRENT ROW = the anchor. Combine them to get exactly the rows you want in each calculation.

Named WINDOW Clause — DRY Windows

If you use the same PARTITION BY / ORDER BY / frame combination in multiple functions, you can name it once with the WINDOW clause and reference it everywhere. The function still goes in the SELECT — the WINDOW clause only stores the window definition.

SELECT
    region, sale_date, event_id, revenue,

    SUM(revenue) OVER region_window     AS total_for_region,
    AVG(revenue) OVER region_window     AS avg_for_region,
    COUNT(*) OVER region_window         AS count_for_region,
    RANK() OVER region_ordered_window    AS rank_in_region

FROM sales

WINDOW
    region_window AS (
        PARTITION BY region
    ),
    region_ordered_window AS (
        PARTITION BY region
        ORDER BY revenue DESC
    )

ORDER BY region, revenue DESC;
WINDOW STORES THE DEFINITION — NOT THE FUNCTION You still write SUM(), AVG(), RANK() etc. in the SELECT. WINDOW only stores the PARTITION BY / ORDER BY / frame. You can reuse the same window with different functions.
CAUTION: ORDER BY AND AGGREGATES Adding ORDER BY to a window definition turns aggregate functions into running calculations. SUM() OVER region_window (no order) gives group total. SUM() OVER region_ordered_window (with order) gives running total. Same function, different window definition, different result.
// NUGGET WINDOW clause = give a name to the OVER() definition. Reuse it across multiple functions. Keeps queries DRY and readable.

NTILE() — Bucket Assignment

NTILE(N) splits the ordered rows in a partition into N roughly equal buckets and assigns each row a bucket number from 1 to N. It labels rows — it does not compute percentile values.

SELECT
    region, sale_date, event_id, revenue,

    NTILE(4) OVER (
        PARTITION BY region
        ORDER BY revenue DESC
    ) AS revenue_quartile

FROM sales
WHERE region = 'South'
ORDER BY sale_date, event_id;
DISPLAY ORDER VS CALCULATION ORDER The NTILE is calculated by revenue ORDER BY inside OVER (DESC = high to low, bucket 1 = top). But the final display ORDER BY is by sale_date. So you may see bucket 2, 4, 1 in the date-ordered output — that's correct. The bucket was assigned by revenue rank, not by date.
NTILE(4) — quartiles
-- bucket 1 = top 25%
-- bucket 2 = next 25%
-- bucket 3 = next 25%
-- bucket 4 = bottom 25%
NTILE(4) OVER (
  ORDER BY cpu_pct
)
NTILE(100) — percentile buckets
-- bucket 1 = bottom 1%
-- bucket 95 = rows in 95th percentile
-- bucket 100 = top 1%
NTILE(100) OVER (
  ORDER BY cpu_pct
)
// NUGGET NTILE labels buckets. It does NOT give you the percentile value. For the actual P95 CPU value, you need percentile_cont — next section.

percentile_cont vs percentile_disc — True Percentiles

These are ordered-set aggregate functions — not window functions, but they live in the same analytical toolbox. They give you the actual value at a percentile threshold.

percentile_cont — interpolated
percentile_cont(0.95)
    WITHIN GROUP (
        ORDER BY cpu_pct
    ) AS cpu_p95

-- May interpolate between
-- two actual data values.
-- Continuous math.
percentile_disc — discrete
percentile_disc(0.95)
    WITHIN GROUP (
        ORDER BY cpu_pct
    ) AS cpu_p95

-- Always returns an actual
-- observed value from the data.

P95 by region and environment (real telemetry pattern):

SELECT
    region,
    env,
    COUNT(*)                                            AS sample_count,
    ROUND(
        percentile_cont(0.95)
            WITHIN GROUP (ORDER BY cpu_pct)::numeric,
        2
    )                                                    AS cpu_p95,
    ROUND(
        percentile_cont(0.50)
            WITHIN GROUP (ORDER BY cpu_pct)::numeric,
        2
    )                                                    AS cpu_median
FROM lab.telemetry_cpu_raw
GROUP BY region, env
ORDER BY cpu_p95 DESC;
// NTILE(100) vs percentile_cont — the difference
ApproachOutput typeUse for
NTILE(100)Bucket label (1–100) per rowLabeling rows: "this row is in the 95th percentile bucket"
percentile_cont(0.95)Single value (the P95 threshold)Finding the value: "P95 CPU is 87.3%"
// NUGGET NTILE labels rows into buckets. percentile_cont computes the actual threshold value. At Citi, you want percentile_cont for SLA reporting (P99 latency = 420ms), not NTILE.

21A

CUME_DIST and PERCENT_RANK — Row Position Functions

CUME_DIST and PERCENT_RANK are row-position functions. They use OVER because every row gets a relative position inside its own partition.

  • CUME_DIST = fraction of rows at or below the current value.
  • PERCENT_RANK = where the current value starts on the ranking ladder.
  • Use them when every row needs relative position inside its group.
// MEMORY LINES CUME_DIST = coverage so far. PERCENT_RANK = rank-start position. CUME_DIST looks after the tie group. PERCENT_RANK looks at where the tie group starts. 
WITH revenue_positions AS (
  SELECT
    region,
    sale_date,
    event_id,
    revenue,
    CUME_DIST() OVER (
      PARTITION BY region
      ORDER BY revenue ASC
    ) AS revenue_cume_dist,
    PERCENT_RANK() OVER (
      PARTITION BY region
      ORDER BY revenue ASC
    ) AS revenue_percent_rank
  FROM sales_events
)
SELECT
  region,
  sale_date,
  event_id,
  revenue,
  ROUND(revenue_cume_dist::numeric, 4) AS revenue_cume_dist,
  ROUND(revenue_percent_rank::numeric, 4) AS revenue_percent_rank
FROM revenue_positions
ORDER BY region ASC, revenue DESC, event_id ASC;

Ties explain the difference. CUME_DIST counts through the end of the tie group. PERCENT_RANK uses where the tie group starts.

// INTERVIEW SENTENCE

“CUME_DIST is coverage-based row positioning. PERCENT_RANK is rank-start positioning. They are both useful, but they answer slightly different percentile-position questions around ties.”

P95 Cutoff vs CUME_DIST Coverage

P95 and CUME_DIST are not competing versions of the same thing. They produce different outputs for different jobs.

// METHOD COMPARISON
MethodOutputBest for
P95 / percentile_contOne cutoff value per groupSLA thresholds, telemetry cutoffs, join-back labeling
CUME_DISTOne relative-coverage value per rowRow-level top-percent flags
PERCENT_RANKOne rank-start value per rowRanking ladder position
NTILEOne bucket label per rowQuartiles, thirds, paging
// NUGGET Percentile gives the cutoff. Join attaches the cutoff. CASE labels the row. 
WITH region_p95 AS (
  SELECT
    region,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY revenue) AS p95_revenue
  FROM sales_events
  GROUP BY region
)
SELECT
  s.region,
  s.sale_date,
  s.event_id,
  s.revenue,
  p.p95_revenue,
  CASE
    WHEN s.revenue >= p.p95_revenue THEN 'At or above P95'
    ELSE 'Below P95'
  END AS p95_band
FROM sales_events AS s
JOIN region_p95 AS p
  ON s.region = p.region
ORDER BY s.region ASC, s.revenue DESC, s.event_id ASC;
WITH revenue_positions AS (
  SELECT
    region,
    revenue,
    CUME_DIST() OVER (
      PARTITION BY region
      ORDER BY revenue ASC
    ) AS revenue_cume_dist
  FROM sales_events
),
region_p95 AS (
  SELECT
    region,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY revenue) AS p95_revenue
  FROM sales_events
  GROUP BY region
),
compare_methods AS (
  SELECT
    r.region,
    CASE
      WHEN r.revenue_cume_dist >= 0.95 THEN 'Top 5%'
      ELSE 'Below Top 5%'
    END AS cume_dist_band,
    CASE
      WHEN r.revenue >= p.p95_revenue THEN 'Top 5%'
      ELSE 'Below Top 5%'
    END AS p95_band
  FROM revenue_positions AS r
  JOIN region_p95 AS p
    ON r.region = p.region
)
SELECT
  cume_dist_band,
  p95_band,
  COUNT(*) AS row_count
FROM compare_methods
GROUP BY cume_dist_band, p95_band
ORDER BY cume_dist_band, p95_band;

Zero disagreements is okay. It just means the data and the business definition lined up neatly.

Owner Priority Scoring Pipeline

This is the owner-priority pipeline:

raw rows -> CUME_DIST -> revenue_band -> review queue -> owner summary -> weighted priority_score -> priority_rank -> recommended_action
WITH revenue_positions AS (
  SELECT
    region,
    salesperson,
    revenue,
    CUME_DIST() OVER (
      PARTITION BY region
      ORDER BY revenue ASC
    ) AS revenue_cume_dist
  FROM sales_events
),
revenue_bands AS (
  SELECT
    region,
    salesperson,
    revenue,
    CASE
      WHEN revenue_cume_dist >= 0.95 THEN 'Top 5%'
      WHEN revenue_cume_dist >= 0.80 THEN 'High'
      WHEN revenue_cume_dist >= 0.20 THEN 'Middle'
      ELSE 'Low'
    END AS revenue_band
  FROM revenue_positions
),
priority_by_salesperson AS (
  SELECT
    region,
    salesperson,
    SUM(CASE WHEN revenue_band = 'Top 5%' THEN 1 ELSE 0 END) AS top_5_count,
    SUM(CASE WHEN revenue_band = 'High' THEN 1 ELSE 0 END) AS high_count,
    SUM(
      CASE
        WHEN revenue_band = 'Top 5%' THEN 3
        WHEN revenue_band = 'High' THEN 1
        ELSE 0
      END
    ) AS weighted_priority_score
  FROM revenue_bands
  WHERE revenue_band IN ('Top 5%', 'High')
  GROUP BY region, salesperson
),
ranked_priority AS (
  SELECT
    region,
    salesperson,
    top_5_count,
    high_count,
    weighted_priority_score,
    RANK() OVER (
      PARTITION BY region
      ORDER BY weighted_priority_score DESC, salesperson ASC
    ) AS priority_rank
  FROM priority_by_salesperson
)
SELECT
  region,
  salesperson,
  top_5_count,
  high_count,
  weighted_priority_score,
  priority_rank,
  CASE
    WHEN weighted_priority_score >= 20 THEN 'Immediate focus'
    WHEN weighted_priority_score >= 15 THEN 'High priority'
    ELSE 'Monitor'
  END AS recommended_action
FROM ranked_priority
ORDER BY region ASC, priority_rank ASC, salesperson ASC;
  • Conditional SUM counts row-level signals by band.
  • Weights create urgency.
  • GROUP BY turns row-level urgency into owner-level priority.
  • RANK creates management order inside each region.
  • CASE at the end turns analytics into a business recommendation.
// MEMORY LINES Banding creates categories. Weights create urgency. GROUP BY turns row-level urgency into owner-level priority. Raw rows -> signals -> scores -> ranked recommendations.

This pattern translates cleanly to sales performance, fraud, customer risk, observability alerts, incident triage, and capacity prioritization.

CTE and Subquery Patterns

Window functions operate on the rows they receive. If you need to pre-process those rows first (deduplicate, summarize, filter), do it in a CTE or subquery before applying the window function.

Pattern 1: Deduplicate first, then number

WITH years AS (
    SELECT DISTINCT year
    FROM summer_medals
)
SELECT
    year,
    ROW_NUMBER() OVER (
        ORDER BY year ASC
    ) AS row_n
FROM years
ORDER BY year;

Without the CTE, ROW_NUMBER() would number each individual medal row — not each unique year.

Pattern 2: Daily summary first, then trend

WITH daily AS (
    SELECT sale_date, SUM(revenue) AS daily_rev
    FROM sales
    GROUP BY sale_date
)
SELECT
    sale_date, daily_rev,
    AVG(daily_rev) OVER (
        ORDER BY sale_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS rolling_7d_avg
FROM daily;
// NUGGET Window functions number/rank/aggregate the rows they receive. Control what rows they receive. Use GROUP BY first when the question is at a summary level. Use DISTINCT first when you want one row per entity.

NULLIF() and Safe Division

Whenever you divide inside a window calculation, you risk division by zero. The defense is NULLIF(denominator, 0).

-- NULLIF(x, 0) means:
-- "if x is 0, return NULL; otherwise return x"
-- NULL / anything = NULL (no crash)
-- 0 / anything = crash

ROUND(
    100.0 * (revenue - previous_revenue)
        / NULLIF(previous_revenue, 0),
    2
) AS pct_change

Why not just WHERE previous_revenue != 0? Because filtering rows out of your result changes your window. The window function might recalculate with different rows. NULLIF keeps the row in the result with a NULL value instead of exploding the query.

DANGEROUS
revenue / previous_revenue
-- Crashes if previous_revenue = 0
SAFE
revenue / NULLIF(previous_revenue, 0)
-- Returns NULL instead of crash
// NUGGET NULLIF(x, 0) is your divide-by-zero airbag. Always use it when dividing by a column that could be zero. NULL is survivable; divide-by-zero crashes the query.

CROSSTAB / Pivoting

CROSSTAB is PostgreSQL's pivot tool from the tablefunc extension. It is a reporting/reshaping tool, not a window function. Window functions calculate values; CROSSTAB changes the shape of the result.

PLAIN ENGLISH CROSSTAB turns tall rows into wide columns. It is like saying: “take the values from one column, such as Year, and make those values become report columns.”

Before using it in PostgreSQL, enable the extension:

CREATE EXTENSION IF NOT EXISTS tablefunc;

The simple form expects a source query with exactly three meaningful columns:

// CROSSTAB 3-COLUMN INPUT RULE
PositionMeaningExample
1Row identifierGender
2Pivot category — values become output columnsYear → "2008", "2012"
3Cell value — what goes inside the pivoted cellsCountry
Before: tall result
Gender   Year   Country
Men      2008   AUS
Men      2012   FRA
Women    2008   RUS
Women    2012   USA
After: wide report
Gender   2008   2012
Men      AUS    FRA
Women    RUS    USA

The output columns "2008" and "2012" come from values in the Year column, but CROSSTAB does not create them automatically. You declare the final shape manually in AS ct (...).

DOLLAR QUOTING The $$ markers start and end a PostgreSQL dollar-quoted string. CROSSTAB receives the inner SQL query as text. StudyBook style: do not put a semicolon inside $$; put the semicolon after the full outer query. DataCamp may accept either style, but this guide uses the cleaner version. 
CREATE EXTENSION IF NOT EXISTS tablefunc;

SELECT *
FROM CROSSTAB($$
  SELECT
    Gender,
    Year,
    Country
  FROM Summer_Medals
  WHERE Year IN (2008, 2012)
    AND Medal = 'Gold'
    AND Event = 'Pole Vault'
  ORDER BY Gender ASC, Year ASC
$$) AS ct (
  Gender VARCHAR,
  "2008" VARCHAR,
  "2012" VARCHAR
)
ORDER BY Gender ASC;

For a pivoted ranking report, calculate the ranking first, then pivot the ranked result:

CREATE EXTENSION IF NOT EXISTS tablefunc;

SELECT *
FROM CROSSTAB($$
  WITH Country_Awards AS (
    SELECT
      Country,
      Year,
      COUNT(*) AS Awards
    FROM Summer_Medals
    WHERE Country IN ('FRA', 'GBR', 'GER')
      AND Year IN (2004, 2008, 2012)
      AND Medal = 'Gold'
    GROUP BY Country, Year
  )

  SELECT
    Country,
    Year,
    RANK() OVER (
      PARTITION BY Year
      ORDER BY Awards DESC
    )::INTEGER AS rank_n
  FROM Country_Awards
  ORDER BY Country ASC, Year ASC
$$) AS ct (
  Country VARCHAR,
  "2004" INTEGER,
  "2008" INTEGER,
  "2012" INTEGER
)
ORDER BY Country ASC;
// NUGGET Simple CROSSTAB reads: row key, pivot category, cell value. The category values fill the manually declared output columns in order.

Multi-Measure Pivot: FILTER / CASE

Basic CROSSTAB is best when each row/category intersection has one cell value.

// ONE VALUE VS MULTIPLE VALUES
ShapeGood fit?Reason
country + year → medalsGoodOne value goes in each cell.
country + year → rankGoodOne value goes in each cell.
country + year → medals and rankAwkwardCROSSTAB wants one cell value, not two measures.

When you need multiple measures, use one of these patterns:

  • Run separate pivots and join them.
  • Use manual pivoting with FILTER.
  • Use manual pivoting with CASE for portability.
  • Use one combined text cell only for a quick display, not for analytics.

In PostgreSQL, FILTER is clean and readable:

WITH country_medals AS (
  SELECT
    year,
    country,
    COUNT(*) AS medals
  FROM summer_medals
  WHERE country IN ('CHN', 'KOR', 'JPN')
    AND medal = 'Gold'
    AND year IN (2004, 2008, 2012)
  GROUP BY year, country
),

country_ranks AS (
  SELECT
    year,
    country,
    medals,
    RANK() OVER (
      PARTITION BY year
      ORDER BY medals DESC
    ) AS rank_n
  FROM country_medals
)

SELECT
  country,

  MAX(medals) FILTER (WHERE year = 2004) AS medals_2004,
  MAX(rank_n) FILTER (WHERE year = 2004) AS rank_2004,

  MAX(medals) FILTER (WHERE year = 2008) AS medals_2008,
  MAX(rank_n) FILTER (WHERE year = 2008) AS rank_2008,

  MAX(medals) FILTER (WHERE year = 2012) AS medals_2012,
  MAX(rank_n) FILTER (WHERE year = 2012) AS rank_2012

FROM country_ranks
GROUP BY country
ORDER BY country;

The portable CASE version uses the same idea:

MAX(CASE WHEN year = 2004 THEN medals END) AS medals_2004,
MAX(CASE WHEN year = 2004 THEN rank_n END) AS rank_2004
// INTERVIEW SENTENCE

“For a simple pivot I need row key, pivot category, and one cell value. If I need multiple measures like medals and rank, I usually use conditional aggregation with FILTER or CASE because it is clearer than forcing multiple values into CROSSTAB.”

ROLLUP

ROLLUP is a GROUP BY extension, not a window function. It adds subtotal rows to a normal grouped result.

MENTAL MODEL ROLLUP is like spreadsheet subtotals. It works best when your columns have a hierarchy, such as Year → Quarter → Month or Country → Gender.

This version keeps the country fixed and rolls up gender inside each country:

SELECT
  Country,
  Gender,
  COUNT(*) AS Gold_Awards
FROM Summer_Medals
WHERE Year = 2004
  AND Medal = 'Gold'
  AND Country IN ('DEN', 'NOR', 'SWE')
GROUP BY Country, ROLLUP(Gender)
ORDER BY Country ASC, Gender ASC;
// GROUP BY Country, ROLLUP(Gender)
CountryGenderGold_AwardsMeaning
DENMen4Detail row
DENWomen15Detail row
DENNULL19Denmark subtotal

ROLLUP(Country, Gender) goes one level further: detail rows, country subtotal rows, and a grand total row.

SELECT
  Country,
  Gender,
  COUNT(*) AS Gold_Awards
FROM Summer_Medals
WHERE Year = 2004
  AND Medal = 'Gold'
  AND Country IN ('DEN', 'NOR', 'SWE')
GROUP BY ROLLUP(Country, Gender)
ORDER BY Country ASC, Gender ASC;
NULL DOES NOT ALWAYS MEAN MISSING In ROLLUP output, NULL often means “subtotal” or “grand total.” Use COALESCE later to show readable labels.
// NUGGET ROLLUP is hierarchical. Column order matters because it decides which subtotal levels are created.

COALESCE

COALESCE() returns the first non-null value from left to right.

SELECT COALESCE(NULL, 'Total');
-- Result: Total

In plain English, COALESCE(gender, 'Total') means: show gender if it exists; otherwise show Total.

With ROLLUP and CUBE, this is especially useful because subtotal rows appear as NULL.

SELECT
  COALESCE(Country, 'All countries') AS Country,
  COALESCE(Gender, 'All genders') AS Gender,
  COUNT(*) AS Awards
FROM Summer_Medals
WHERE Year = 2004
  AND Medal = 'Gold'
  AND Country IN ('DEN', 'NOR', 'SWE')
GROUP BY ROLLUP(Country, Gender)
ORDER BY Country ASC, Gender ASC;

Before COALESCEAfter COALESCEMeaning
DEN / NULLDEN / All gendersCountry subtotal
NULL / NULLAll countries / All gendersGrand total
DISPLAY ONLY COALESCE does not create totals. ROLLUP/CUBE create the subtotal rows. COALESCE only changes how the NULL labels appear.

COALESCE is also handy when LAG, LEAD, or a pivot returns missing values.

CASE Statements — General Syntax

CASE is SQL's built-in conditional expression. It lets you create a new value based on rules, similar to “if / else if / else” logic in programming.

PLAIN ENGLISH Read CASE as: “When this condition is true, return this value. Otherwise, try the next condition. If nothing matches, return the ELSE value.”

The most common form is the searched CASE. This is the flexible version because each WHEN can test a full condition.

CASE
  WHEN condition_1 THEN result_1
  WHEN condition_2 THEN result_2
  WHEN condition_3 THEN result_3
  ELSE fallback_result
END

Example: convert raw medal counts into business-friendly buckets:

SELECT
  Country,
  COUNT(*) AS Gold_Awards,
  CASE
    WHEN COUNT(*) >= 20 THEN 'High'
    WHEN COUNT(*) >= 10 THEN 'Medium'
    WHEN COUNT(*) > 0 THEN 'Low'
    ELSE 'None'
  END AS award_band
FROM Summer_Medals
WHERE Year = 2012
  AND Medal = 'Gold'
GROUP BY Country
ORDER BY Gold_Awards DESC;
// CASE EVALUATION ORDER
StepWhat SQL checksWhat happens
1WHEN COUNT(*) >= 20If true, returns High and stops.
2WHEN COUNT(*) >= 10Only checked if step 1 was false.
3WHEN COUNT(*) > 0Only checked if steps 1 and 2 were false.
4ELSE 'None'Used only when no WHEN condition matches.
ORDER MATTERS CASE returns the first matching WHEN. Put the most specific or highest-priority condition first. If you put WHEN COUNT(*) > 0 before WHEN COUNT(*) >= 20, every positive count would become Low.

You will usually see CASE in four places:

// WHERE CASE IS COMMONLY USED
LocationUse caseExample idea
SELECTCreate a new calculated label/column.risk_band, award_band, status_label
ORDER BYForce business sorting instead of alphabetic sorting.Men, Women, Total
Conditional aggregationCount or sum only rows that match a condition.SUM(CASE WHEN ... THEN 1 ELSE 0 END)
Manual pivotTurn categories into separate columns.MAX(CASE WHEN year = 2012 THEN medals END)

CASE in SELECT: create readable categories:

SELECT
  Country,
  Medals,
  CASE
    WHEN Medals >= 20 THEN 'High performer'
    WHEN Medals >= 10 THEN 'Medium performer'
    ELSE 'Watch list'
  END AS performance_label
FROM Country_Medals;

CASE for conditional aggregation: count rows by condition without filtering away the other rows:

SELECT
  Country,
  SUM(CASE WHEN Medal = 'Gold' THEN 1 ELSE 0 END) AS gold_count,
  SUM(CASE WHEN Medal = 'Silver' THEN 1 ELSE 0 END) AS silver_count,
  SUM(CASE WHEN Medal = 'Bronze' THEN 1 ELSE 0 END) AS bronze_count
FROM Summer_Medals
GROUP BY Country;

CASE for manual pivoting: turn row values into report columns:

SELECT
  Country,
  MAX(CASE WHEN Year = 2004 THEN Medals END) AS medals_2004,
  MAX(CASE WHEN Year = 2008 THEN Medals END) AS medals_2008,
  MAX(CASE WHEN Year = 2012 THEN Medals END) AS medals_2012
FROM Country_Medals
GROUP BY Country;
Searched CASE
CASE
  WHEN revenue >= 1000 THEN 'High'
  WHEN revenue >= 500 THEN 'Medium'
  ELSE 'Low'
END
Simple CASE
CASE medal
  WHEN 'Gold' THEN 3
  WHEN 'Silver' THEN 2
  WHEN 'Bronze' THEN 1
  ELSE 0
END
ELSE IS OPTIONAL BUT IMPORTANT If no WHEN matches and you did not write ELSE, CASE returns NULL. That may be fine in a manual pivot, but it can surprise you in labels, counts, and report columns.
// INTERVIEW SENTENCE

“I use CASE when I need conditional logic inside SQL — for readable labels, business sort order, conditional aggregation, and manual pivot-style reporting. The key is that CASE checks conditions from top to bottom and returns the first match.”

Sometimes the data is correct, but the display order is ugly. For example, alphabetical sorting can show this:

Men
Total
Women

The desired business order is usually:

Men
Women
Total

Use COALESCE for the label and CASE in ORDER BY for the position.

STRING_AGG

STRING_AGG compresses many rows into one text list. It is useful after ranking when the report wants one row instead of many rows.

Before
Country   Rank
USA       1
RUS       2
AUS       3
After
USA, RUS, AUS
WITH Country_Medals AS (
  SELECT
    Country,
    COUNT(*) AS Medals
  FROM Summer_Medals
  WHERE Year = 2000
    AND Medal = 'Gold'
  GROUP BY Country
),

Country_Ranks AS (
  SELECT
    Country,
    RANK() OVER (
      ORDER BY Medals DESC
    ) AS Rank
  FROM Country_Medals
)

SELECT
  STRING_AGG(Country, ', ' ORDER BY Rank) AS Top_Countries
FROM Country_Ranks
WHERE Rank <= 3;

The pattern is:

  • RANK() creates the order.
  • WHERE Rank <= 3 filters the top rows.
  • STRING_AGG(... ORDER BY Rank) compresses them into one ordered list.
ORDER MATTERS If you omit ORDER BY inside STRING_AGG, the list order may not be reliable.

Final Oral Defense Q&A

// Q1

GROUP BY vs PARTITION BY? GROUP BY collapses rows. PARTITION BY keeps detail rows and calculates inside buckets.

// Q2

What does ORDER BY inside OVER do? Window ORDER BY calculates. Final ORDER BY displays.

// Q3

Why do ranking aliases need a CTE before filtering? Because the window result is created after the select list. Calculate first, filter second.

// Q4

Why avoid unique tie-breakers in RANK and DENSE_RANK? Because they break real ties and create fake uniqueness.

// Q5

What is the LAST_VALUE trap? LAST_VALUE needs the full frame. Without it, the default frame often stops at the current row.

// Q6

ROWS vs RANGE? ROWS = physical rows. RANGE = value peers.

// Q7

NTILE vs P95? NTILE creates bucket labels. P95 creates a cutoff value.

// Q8

Why does percentile_cont use WITHIN GROUP? Because it is an ordered-set aggregate and needs an ordered value list.

// Q9

What does CUME_DIST mean? It means coverage so far: what fraction of rows are at or below this value.

// Q10

What does PERCENT_RANK mean? It means rank-start position: where the current value starts on the ranking ladder.

// Q11

Why do CUME_DIST and PERCENT_RANK differ around ties? CUME_DIST looks after the tie group. PERCENT_RANK looks at where the tie group starts.

// Q12

What was the final owner-priority pipeline? Row-level percentile signals became business bands, bands became a review queue, review rows became weighted owner-level priority, and CASE turned the output into a management recommendation.

// Q13

Shortest memory line? Raw rows -> signals -> scores -> ranked recommendations.
