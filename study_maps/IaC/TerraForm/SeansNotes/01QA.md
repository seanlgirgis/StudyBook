

# 00 Why Terraform Exists

## 1.0 Why did Infrastructure as Code become necessary?

Before IaC, infrastructure was often created manually, documented loosely,
or automated through scattered scripts and tribal knowledge. That made it hard
to reproduce, audit, maintain, version, and safely scale across environments.

Infrastructure as Code became the answer because cloud environments grew too
large and complex to manage reliably by hand. IaC moves infrastructure into
reviewable, version-controlled definitions so teams can repeat changes,
track them, and reduce configuration drift.

## 2.0 Why is manual console work risky as the main workflow?

Manual console work means clicking through the cloud console to create or
change infrastructure. It may work once, but it is hard to repeat exactly,
hard to review before the change, and hard to audit afterward.

When problems happen, people may make quick fixes that are never documented.
It also becomes difficult to reproduce the same setup across dev, test, and
production. That makes manual console work risky, bug-prone, and very friendly
to drift.

## 3.0 Why are scattered scripts and tribal knowledge better than pure clicking, but still not enough?

Scattered scripts are better than pure clicking because they introduce some
automation and repeatability. A script can capture steps and run them more
consistently than a person clicking through a console.

But scripts can become their own maintenance burden. As the environment grows,
teams may end up with many scripts, hidden assumptions, unclear ownership, and
tribal knowledge around how to run them safely.

At some point, if you build enough structure around scripts to handle inputs,
state, review, reuse, and environments, you are basically inventing your own
Infrastructure as Code system.

## 4.0 Why does cloud growth make manual work and scattered scripts break down?

Cloud growth makes manual work and scattered scripts break down because the
number of resources, configurations, environments, and relationships keeps
expanding.

At small scale, one strong engineer may be able to keep things organized with
scripts and documentation. But as the environment grows, that knowledge becomes
hard to transfer. If the person who understands the scripts leaves, the team may
struggle to understand what is documented, what is assumed, and what is missing.

Infrastructure as Code helps because it moves the environment definition into a
more structured, declarative format. With Terraform HCL, teams describe what
resources they want and how they should be configured, while Terraform figures
out the change steps. That makes infrastructure easier to review, maintain,
repeat, and transfer between team members.

## 5.0 What does Infrastructure as Code mean, and why is it better than manual setup?

Infrastructure as Code means defining infrastructure in files instead of
creating it manually through the console.

The infrastructure definition becomes structured, reviewable, and usually
version-controlled. In a declarative IaC tool like Terraform, you describe what
resources you want and how they should be configured, and the tool figures out
the steps needed to reach that desired state.

That makes infrastructure easier to repeat, review, maintain, audit, and
transfer between team members.

## 6.0 What is Terraform, and how does it fit into Infrastructure as Code?

Infrastructure as Code is the concept of defining infrastructure in files
instead of creating it manually through a console. Those definitions become
structured, reviewable, repeatable, and usually version-controlled.

Terraform is one major implementation of Infrastructure as Code. It uses a
declarative configuration language called HCL, where you describe the desired
infrastructure and Terraform figures out the changes needed to reach that state.

One major advantage of Terraform is that it works with many providers, so teams
can use a similar workflow across AWS, Azure, Google Cloud, Kubernetes,
observability tools, and other platforms.

## 7.0 What is CloudFormation, and how is it different from Terraform?

CloudFormation is AWS's native Infrastructure as Code service. It uses YAML
or JSON templates to describe AWS infrastructure.

The main difference is scope. CloudFormation is AWS-native and focused on AWS
resources, while Terraform is multi-provider and can manage resources across
AWS, Azure, Google Cloud, Kubernetes, observability tools, and many other
platforms.

## 8.0 What is Ansible, and how is it different from Terraform?

Ansible is mainly an automation, orchestration, and configuration-management
tool. It is commonly used for software installation, server configuration,
deployments, operational tasks, and some provisioning.

Terraform is mainly an Infrastructure as Code tool. Its strength is defining,
provisioning, and managing infrastructure resources in a repeatable,
declarative workflow.

So while there is some overlap, I usually think of Terraform as stronger for
creating and managing infrastructure, and Ansible as stronger for configuring
systems and automating tasks after infrastructure exists.


## 9.0 What is Pulumi, and how is it different from Terraform?

Pulumi and Terraform serve a similar purpose because both are Infrastructure
as Code tools.

The big difference is the language model. Pulumi lets teams define
infrastructure using general-purpose programming languages such as Python,
TypeScript, Go, and C#. Some teams like this because they can use the same
language and software engineering patterns they already use elsewhere.

Terraform uses HCL, which is a declarative configuration language designed
specifically for defining infrastructure.

## 10 What is OpenTofu, and how is it related to Terraform?

OpenTofu is an open-source, Terraform-compatible fork that came out after
HashiCorp changed Terraform's licensing.

The goal of OpenTofu is to keep a more community-governed open-source path for
teams that like the Terraform-style workflow and want compatibility with the
Terraform ecosystem.

# 01 Terraform 1000-Foot View

## 11 What is Terraform simple core Idea?
- You describe the infrastructure you want.
- Terraform compares that desired state to what exists.
- Terraform shows a plan.
- You review it.
- Terraform applies the approved change.
- Terraform tracks what it manages in state.

## 13 What is the Mental Model of Terraform?

- HCL files       = what I want
- Provider        = how Terraform talks to AWS/Azure/etc.
- Resources       = what Terraform manages
- Plan            = preview
- Apply           = execute
- State           = memory
- Drift           = real world changed outside Terraform
- Modules         = reusable patterns
- Team safety     = review, locking, backend, version control

## 14 Why does Terraform matter after a team already understands Infrastructure as Code?

Terraform matters because it gives teams a practical tool for applying
Infrastructure as Code. It makes infrastructure repeatable, reviewable,
version-controlled, and less dependent on manual clicking.

It also works across many providers, so teams can use a consistent workflow
for AWS, Azure, Kubernetes, observability tools, and other platforms.


## 15 In Terraform terms, what does Infrastructure as Code mean?

In Terraform terms, Infrastructure as Code means defining the desired
infrastructure in configuration files. Terraform compares that desired state
with the current real-world infrastructure, shows a plan, and then applies
controlled changes after review.

## 16 What is desired state in Terraform?

Desired state in Terraform means the infrastructure described in the HCL files:
what resources should exist, how they should be configured, and how they relate
to each other.

Terraform compares that desired state with what currently exists. Then it
creates a plan showing what needs to be created, changed, or removed. After the
plan is reviewed and approved, Terraform applies the change and tracks the
managed resources in state.

## 17 What is a Terraform provider?

A Terraform provider is the plugin that connects Terraform to a platform or
service, such as AWS, Azure, Google Cloud, Kubernetes, Datadog, or Grafana.

The provider knows how to call that platform's API so Terraform can create,
read, update, or delete resources there.

## 18. What is a Terraform resource?

A Terraform resource is an infrastructure object that Terraform manages,
such as an S3 bucket, EC2 instance, IAM role, VPC, log group, dashboard,
or alert.

The resource block describes what should exist and how it should be configured.

## 19. Provider, Resource .. Differntiate?

- Provider = how Terraform talks to the platform.
- Resource = what Terraform manages on that platform.

## 20 What is terraform plan, and why is it important?

terraform plan previews what Terraform intends to do before it makes any real
changes. It compares the desired state in the configuration with the current
state and shows what it would create, update, or destroy.

This is important because some changes can be risky, such as replacing a
resource, deleting something, changing permissions, or affecting data. Reviewing
the plan helps the team understand the blast radius before running apply.

##21 What is terraform apply, and why should it be treated carefully?

terraform apply is the command that makes the reviewed Terraform plan real.
It creates, updates, or destroys infrastructure resources based on the approved
configuration.

It should be treated carefully because apply changes real environments. You
should not run it casually, especially in shared or production environments,
unless the plan has been reviewed and the target environment is correct.

##22 What is Terraform state, and why is it important?

Terraform state is Terraform's memory of the infrastructure it manages.
It records how the Terraform configuration maps to real cloud resources.

State is important because Terraform uses it to compare the desired
configuration with what it already manages, decide what needs to change,
and avoid recreating or losing track of resources.


## 23 What is Terraform drift?
Terraform drift happens when real infrastructure is changed outside Terraform,
so the actual environment no longer matches the Terraform configuration or
state.

Drift can cause confusion because Terraform may later show unexpected changes
in the plan. It also creates operational risk because the real environment is
no longer fully represented by the code.

## 24 What is a Terraform module, and why do teams use modules?

A Terraform module is a reusable package of Terraform configuration.

It is Terraform's way to support reuse, encapsulation, and standardization.
Teams use modules to avoid copying the same resource code across projects and
to enforce common patterns for naming, tagging, security, networking, or
environment setup.

A module can accept inputs through variables and expose useful results through
outputs. That makes Terraform code cleaner, easier to reuse, and easier to
govern across environments.

## 25 Why does Terraform need team safety practices?

Terraform needs team safety practices because it can create, modify, or destroy
real infrastructure. In a team environment, unsafe Terraform use can cause
conflicting changes, broken environments, accidental deletes, permission
mistakes, or state corruption.

Good team safety means using version control, pull request review, plan review,
remote state, state locking, access control, and disciplined apply workflows.

# 02 Terraform Core Workflow

## 26 Tell me about Terraform files?

- main.tf       = main resources / structure
- providers.tf = provider setup, like AWS
- variables.tf = inputs
- outputs.tf   = values Terraform shows after running
- versions.tf  = Terraform/provider version constraints
- tfvars       = actual values for variables


## 27 In the Terraform workflow, what does “write configuration” mean?

“Write configuration” means creating Terraform `.tf` files that describe the
desired infrastructure state. These files become the source of truth for what
Terraform should manage, such as providers, resources, variables, and outputs.

## 28 What does `terraform init` do, and why is it usually the first command?

terraform init prepares the working directory so Terraform can operate.
It downloads the required providers, initializes modules, and configures the
backend used for state.

It is usually the first command because Terraform needs those pieces in place
before it can validate, plan, or apply the configuration.


## 29 What does `terraform fmt` do, and why does it matter?

terraform fmt formats Terraform configuration files into the standard HCL
style. It reads `.tf` and `.tfvars` files and rewrites them with consistent
spacing, indentation, and layout.

It matters because consistent formatting makes Terraform code easier to read,
review, compare in Git, and maintain as a team.

## 30 What does `terraform validate` do, and how is it different from `terraform fmt`?

terraform validate checks whether the Terraform configuration is syntactically
valid and internally consistent. It can catch issues like missing required
arguments, invalid references, or incorrect block structure.

terraform fmt is different because it only standardizes formatting, such as
spacing, indentation, and layout.

## 31 In the core workflow, what does `terraform plan` do?

terraform plan previews what Terraform intends to create, change, destroy,
or replace before it touches real infrastructure.

It compares the desired configuration with the current state and shows the
actions Terraform would take. This makes plan the main safety checkpoint before
apply.

### Common plan symbols:
```text
+     create
~     update in place
-     destroy
-/+   destroy and recreate / replace
<=    read data source
```

## 32 Why should humans review the Terraform plan before apply?
Humans should review the Terraform plan before apply because apply can create,
modify, replace, or destroy real infrastructure. some changes can be expensive, disruptive, or hard to reverse.

The plan review helps catch dangerous or unintended changes, such as deleting
a resource, replacing something that contains data, changing permissions, or
applying to the wrong environment.

## 33 In the core workflow, what does `terraform apply` do?

In the core workflow, `terraform apply` performs the approved infrastructure
changes. It uses the provider plugins to call the target platform APIs and
create, update, replace, or destroy real resources.

That is why apply should only happen after the plan is reviewed and the target
environment is confirmed.

## 34 What are Terraform outputs, and why are they useful?

Terraform outputs expose useful values after Terraform creates or reads
infrastructure.

They are useful because they show important resulting values to people or
downstream automation, such as resource IDs, endpoint names, URLs, bucket names,
IP addresses, or connection details.


## 35 How does Terraform handle infrastructure changes after the first apply?

Terraform is not only for initial infrastructure creation. After the first
apply, Terraform continues to manage the infrastructure over time.

It uses state to remember what it manages, compares future configuration
changes against that state and the real environment, and then creates a new
plan showing what needs to be updated, replaced, created, or destroyed.

Terraform can reveal drift during plan, so the team can decide whether to
reconcile the real environment back to the code or update the code to match an
approved change.


## 36 What does `terraform destroy` do, and why is it dangerous?

terraform destroy removes infrastructure that Terraform manages.

It is dangerous because it can delete real resources, including resources that
applications, data pipelines, monitoring, or users depend on. It should only be
used with clear intent, review, the correct workspace/environment, and a cleanup
plan.

# 03 Terraform State, Drift, and Backends

## 37 What is Terraform state, and what did our lab show about it?

Terraform state is Terraform’s stored record of the infrastructure it manages.
It maps Terraform configuration to real infrastructure, so Terraform knows what
it already created, what it tracks, and what may need to change.

Our lab showed this clearly: after apply, `terraform state list` showed the
managed resource. After destroy, state became empty. Then Terraform planned to
recreate the resource because the configuration still said it should exist.

## 38 Why does Terraform need state at all?

Terraform needs state so it can remember what it manages and compare the
desired configuration against the current managed infrastructure.

State helps Terraform determine the delta: what needs to be created, changed,
replaced, or destroyed to bring the environment back to the desired state.
It also helps expose drift when the real environment no longer matches what
Terraform expects.

## 39 What is local state, and when is it okay or risky?

Local state is Terraform state stored on the machine running Terraform,
usually in a `terraform.tfstate` file.

Local state is fine for learning, experiments, and single-user practice labs.
It becomes risky for teams because the state is not shared, protected, locked,
or centrally controlled. Different people could end up with different views of
what Terraform manages.

## 40 What is remote state, and why do teams use it?

Remote state means Terraform stores its state in a shared backend instead of
only on one developer's machine.

Teams use remote state so everyone works from the same trusted record of what
Terraform manages. It helps avoid different local versions of infrastructure
reality.

Remote state also supports safer workflows when combined with access control,
versioning, encryption, and state locking.

## 41 What is Terraform state locking, and why does it matter?

Locking prevents multiple Terraform runs from writing state at the same time.
Concurrent state writes can corrupt or confuse state. State locking protects 
teams from conflicting Terraform runs. Locking is important because it prevents 
two users or pipelines from changing state at the same time.
one run holds lock, another run waits/fails instead of writing concurrently. 
Force-unlock exists but is a careful recovery action.

## 42. What is a Terraform backend?

A Terraform backend controls where Terraform stores state.

A local backend stores state on the local machine. A remote backend stores state
in a shared location, such as Terraform Cloud, S3, Azure Storage, or another
supported backend.

Teams use remote backends so everyone works from the same trusted state instead
of separate local state files. Remote backends can also support access control,
versioning, and locking depending on the backend.

## 43. What is Terraform drift, and why does it matter?

Terraform drift happens when real infrastructure changes outside the Terraform
workflow, usually through manual console changes, scripts, or another tool.

Drift matters because it creates a mismatch between the Terraform configuration,
Terraform state, and the real environment. The next Terraform plan may show
unexpected differences, and the team has to decide whether to bring the real
environment back to the code or update the code to reflect an approved change.

## 44. What does Terraform refresh do, and how does it relate to drift?

Terraform refresh updates Terraform's understanding of the real infrastructure.

Before planning or applying, Terraform checks the current condition of the
managed resources and updates state with what it finds. This helps Terraform
compare the desired configuration against the current managed reality.

Refresh is related to drift because it can reveal that the real environment has
changed outside Terraform.

## 45. What is Terraform import, and why must it be done carefully?

Terraform import brings an existing resource under Terraform management by
connecting that real resource to a Terraform resource address in state.

It is used when the resource already exists but was not originally created by
Terraform. After import, Terraform can track it as part of the managed
infrastructure.

Import must be done carefully because importing only connects the real resource
to Terraform state. The Terraform configuration still needs to accurately
describe that resource. If the code does not match the real object, the next
plan may try to change, replace, or destroy something unexpectedly.

## 46 Why is Terraform state sensitive and risky?

Terraform state is sensitive because it can contain information from managed
infrastructure, including IDs, attributes, connection details, and sometimes
sensitive values.

State is risky because anyone who can read the state may see information that
should not be public. That is why state should be protected with access control,
encryption, controlled remote backends, and disciplined handling.

State files should not be casually committed to Git, shared by email, or exposed
through loose file permissions.

## 47 What kinds of Terraform state mistakes are dangerous?

Terraform state mistakes include deleting, corrupting, exposing, or incorrectly
modifying state. Bad state handling can lead to unexpected plans, broken
resource tracking, accidental infrastructure changes, or security exposure.

State should not be treated as a throwaway file. Teams should avoid randomly
editing state, deleting it blindly, committing it to Git, force-unlocking active
runs, or importing resources to the wrong Terraform address.

# 04 Terraform Providers and Resources

## 48 Terraform Provider what it is?

A Terraform provider is the integration layer between Terraform and a platform
or service. Terraform needs providers because Terraform core does not natively
know every platform API.

For example, Terraform can say, “manage an AWS S3 bucket,” but the AWS provider
knows the specific AWS API calls needed to create, read, update, or delete that
bucket.

## 49 What is the AWS provider in Terraform?

The AWS provider is the Terraform plugin that lets Terraform manage AWS
resources. It knows how to communicate with AWS APIs for services such as S3,
IAM, VPC, EC2, Lambda, CloudWatch, and other AWS services.

It is especially relevant for data engineering, cloud, platform, and
observability work because many pipelines and monitoring systems depend on AWS
infrastructure.

```
provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "raw_data" {
  bucket = "example-raw-data-bucket"
}
```

## 50 What is provider configuration, and what kinds of settings can it include?

Provider configuration tells Terraform how to connect to the target platform.

For AWS, it may include settings like region, default tags, profile, or
authentication method. The provider configuration should not hardcode secrets.
Credentials should usually come from safer sources such as environment
variables, cloud profiles, role-based access, or CI/CD secrets management.

```code
provider "aws" {
  region = "us-east-1"
}
```
