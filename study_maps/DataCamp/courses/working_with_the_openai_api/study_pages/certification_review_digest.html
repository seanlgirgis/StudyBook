2. Know This Cold

ConceptMeaning
systemBehavior, scope, and guardrails
userThe human request
assistantA model reply or example answer
temperatureControls variation; lower is steadier, higher is more creative
max_completion_tokensOutput ceiling; may truncate the answer
finish_reasonWhy generation stopped
prompt_tokensInput tokens
completion_tokensOutput tokens

3. Decision Rules

  • Use low temperature for classification, extraction, factual summaries, and repeatable support answers.
  • Use higher temperature for brainstorming, naming, slogans, and creative variation.
  • Use few-shot examples when labels, scoring, tone, or exact format matter.
  • Use a system guardrail to define both allowed scope and refusal behavior.
  • Do not append a reply when finish_reason == "length".
  • Resend prior messages when a follow-up depends on earlier context.

4. High-Value Traps

Swapped roles

Behavior instructions belong to system; the human request belongs to user.

Fake memory

The API does not remember. Your program must preserve and resend the history.

Truncated history

A cut-off reply can damage later context if appended blindly.

Bad examples

Few-shot examples teach wording, format, judgment, and mistakes.

Tokens are not words

Input and output are counted separately, and token count is only loosely related to word count.

Creativity risk

High temperature can invent unsupported product claims.

5. Fast Review Questions

  1. Where is generated text found in the response object?
  2. Which role defines behavior and guardrails?
  3. Why does input-token usage grow during a multi-turn chat?
  4. What is the difference between zero-shot and few-shot prompting?
  5. What does finish_reason == "length" mean?
  6. Why should a classification task usually use low temperature?
  7. Why should a real API key stay outside source code?
