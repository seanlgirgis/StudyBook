1. Big Picture

A production AI feature is more than a model call. The application must prepare a valid request, extract the useful result, convert it into a format that downstream code can consume, recover from failures, and control request volume and token usage.

User or upstream system | v Validate and prepare input | v OpenAI API request | v Decode response / parse JSON | v Validate result and handle errors | v Return data to the next application step

Structured Requests and Responses

Specify the model, messages, and response format so another application can reliably consume the result.

Errors and Exceptions

Recognize common API failures and catch them without crashing the whole application.

Rate Limits, Retry, and Batching

Use exponential backoff, fewer calls, and token measurement to stay within service limits.

Token Control

Measure and reduce input size so requests fit model limits and remain efficient.

Section punchline: The API call is one step; the application becomes dependable only when parsing, validation, recovery, and usage controls surround it.

2. Structured Requests and Responses

For integration with external systems, ask for a standardized response instead of relying on free-form prose. A Chat Completions response is a structured object: the first generated choice is in response.choices[0], the assistant message is in .message, and the text is in .content. JSON mode is enabled with response_format, and the prompt must still clearly request JSON.

from openai import OpenAI
import json

client = OpenAI()

response = client.chat.completions.create(
    model="gpt-4o-mini",
    messages=[
        {
            "role": "user",
            "content": (
                "Return JSON with a books array. Each item must contain "
                "title and author. Notes: The Beholders by Hester Musson; "
                "The Mystery Guest by Nita Prose."
            ),
        }
    ],
    response_format={"type": "json_object"},
)

raw_content = response.choices[0].message.content

if raw_content is None:
    raise ValueError("The model returned no content.")

data = json.loads(raw_content)
print(data)

print(response.model)
print(response.choices[0].finish_reason)
print(response.usage)
What to notice: response.choices[0] is the whole first choice object; response.choices[0].message.content is only the assistant text. JSON mode produces machine-readable text, but your code must still parse and validate required keys, types, and cardinality before using the result.

3. Errors and Exceptions

Errors differ by cause. Connection and timeout errors are often temporary; rate-limit errors require pacing or reduced load; authentication errors require a valid active key; bad-request errors usually mean malformed or unsupported parameters. Specific except blocks let the application provide a useful response while a final generic handler catches unexpected failures.

from openai import (
    APIConnectionError,
    APITimeoutError,
    AuthenticationError,
    BadRequestError,
    RateLimitError,
)

try:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": "Summarize this text."}],
    )
    print(response.choices[0].message.content)
except AuthenticationError:
    print("Check that the API key is valid and active.")
except BadRequestError as exc:
    print(f"Review the request parameters: {exc}")
except (APIConnectionError, APITimeoutError):
    print("The service could not be reached. Try again shortly.")
except RateLimitError:
    print("Request limit reached. Retry with backoff.")
except Exception as exc:
    print(f"Unexpected error: {exc}")
Common trap: Do not catch only Exception and hide every failure behind one vague message. Catch known API errors first so the application can respond appropriately.

4. Rate Limits, Retry, and Batching

Rate limits may be triggered by too many requests in a period or too many tokens. Use exponential backoff for temporary failures, combine related work into one request when appropriate, and count tokens before sending unusually large prompts.

Technique Use it when Important caution
Retry with exponential backoff A temporary rate-limit, timeout, or connection failure may succeed later. Set a maximum number of attempts; never retry forever.
Batch related inputs Several small requests can be answered together with clear instructions. One request containing many user messages is different from looping over many separate API calls.
Count input tokens with tiktoken The application should reject or shorten an unusually large prompt before sending it. len(encoding.encode(message["content"])) counts message text, while actual prompt usage may also include message-format overhead.
Limit output tokens You need to bound response length, latency, or cost. When finish_reason == "length", the response was truncated and should not be treated as complete.

5. Worked Example

This pattern combines input-token checking, one batched request, and bounded retry. Several kilometer measurements are placed into one message list and returned as a single table.

import tiktoken
from openai import OpenAI
from tenacity import retry, stop_after_attempt, wait_random_exponential

client = OpenAI()

@retry(
    wait=wait_random_exponential(min=5, max=40),
    stop=stop_after_attempt(4),
)
def get_response(messages: list[dict[str, str]]) -> str:
    response = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=messages,
    )
    return response.choices[0].message.content or ""

measurements = [5, 10, 25]
messages = [{
    "role": "system",
    "content": (
        "Convert these measurements from kilometers to miles "
        "and present the results in a table."
    ),
}]

for measurement in measurements:
    messages.append({
        "role": "user",
        "content": str(measurement),
    })

encoding = tiktoken.encoding_for_model("gpt-4o-mini")
input_tokens = sum(
    len(encoding.encode(message["content"]))
    for message in messages
)

if input_tokens <= 100:
    print(get_response(messages))
else:
    print("Message exceeds token limit")
Result: One request carries a system instruction plus several related inputs, the application checks approximate input size before sending, and Tenacity limits recovery attempts if a temporary failure occurs.

6. Validation and Troubleshooting

  • Confirm that the selected model is available and supported for the requested parameters.
  • Parse JSON with json.loads() and verify required keys and value types before passing data downstream.
  • Log enough error context for troubleshooting without exposing API keys, personal data, or sensitive prompts.
  • Measure input tokens with tiktoken.encoding_for_model() before sending large prompts, and compare actual usage afterward with response.usage.
  • Inspect response.choices[0].finish_reason; stop normally means completion, while length means the output limit cut the answer off.
Red flag: A response printed successfully is not proof that the application is reliable. Missing validation, unlimited retries, broad silent exception handling, or ignoring finish_reason="length" can hide serious failures.

7. Common Mistakes

Assuming JSON mode guarantees the exact schema JSON mode helps produce valid JSON, but the application must still validate required fields, types, and allowed values.
Retrying every error Retry only failures that may be temporary. Invalid authentication and malformed requests normally require a code or configuration fix.
Looping over many tiny requests by default When the task permits it, batch related inputs into one well-instructed request. Keep the batch small enough to fit token limits and remain easy to validate.
Leaving the DataCamp API-key placeholder in local code OpenAI(api_key="<OPENAI_API_TOKEN>") sends the placeholder literally and produces a 401 error. In the local lab, use OpenAI() so the SDK reads OPENAI_API_KEY from the environment.
Mixing tabs and spaces inside try/except Python can raise TabError: inconsistent use of tabs and spaces in indentation. Use four spaces consistently for every nested line.

8. Interview Translation

What makes an OpenAI API call production-ready? A production-ready call has validated input, explicit instructions, predictable output formatting, safe response parsing, targeted exception handling, bounded retries, observability, and token or rate-limit controls.
How would you handle rate limits? I would distinguish request-frequency limits from token-volume limits, apply exponential backoff with a maximum attempt count, batch compatible work, reduce unnecessary tokens, and monitor repeated failures.
Why prefer structured JSON output? Structured output gives downstream code stable fields to parse and validate. It reduces brittle text extraction, but it still requires schema validation before the data is trusted.
How do you control token usage? I estimate input size with the model tokenizer, reject or shorten oversized prompts, set an output-token limit, inspect finish_reason for truncation, and record actual usage from the response.

9. Memory Review

Section summary
  1. Request clearly: model, messages, instructions, and response format must agree.
  2. Decode deliberately: access the response content, parse it, and validate its structure.
  3. Handle expected failures specifically, then use a final generic exception handler for unknown problems.
  4. Control load with bounded retry, batching, input-token measurement, output limits, and finish-reason checks.
