1. Big Picture

A schema is a set of decisions about grain, dependencies, reuse, and query cost. A star schema keeps dimensions wide and directly connected to the fact table for simpler queries. A snowflake schema normalizes dimension hierarchies into additional tables, reducing repeated values but increasing join depth. Normal forms provide a disciplined way to decide which attributes belong together.

Star and Snowflake Schemas

A star schema favors direct fact-to-dimension joins; a snowflake schema further normalizes dimension hierarchies.

Normalization and Denormalization

Normalization removes repeated groups and enforces consistency; denormalization intentionally repeats data to simplify or accelerate reads.

First, Second, and Third Normal Form

1NF, 2NF, and 3NF progressively eliminate repeating values, partial dependencies, and transitive dependencies.

Data Integrity and Anomalies

Poor dependency design produces update, insertion, and deletion anomalies.

Section punchline: Design from grain and dependencies first. Choose star versus snowflake and normalized versus denormalized structures as explicit workload trade-offs.

2. Star and Snowflake Schemas

In a star schema, a central fact table records business events or measurements and connects directly to descriptive dimensions through foreign keys. Facts change frequently and contain measures such as sales amount or quantity. Dimensions change less often and describe the who, what, where, and when. A snowflake schema starts from the same fact table but splits repeating dimension attributes into related subdimensions. A store can reference a city, the city a state, and the state a country. This stores hierarchy members once and improves consistency, but every split adds joins and query complexity.

-- Star: store attributes remain together
SELECT f.sales_id, s.store_address, s.city, s.state,
       s.country, f.sales_amount
FROM fact_booksales AS f
JOIN dim_store_star AS s ON f.store_id = s.store_id;

-- Snowflake: geography is normalized
SELECT f.sales_id, s.store_address, c.city, st.state,
       co.country, f.sales_amount
FROM fact_booksales AS f
JOIN dim_store_sf AS s    ON f.store_id = s.store_id
JOIN dim_city_sf AS c     ON s.city_id = c.city_id
JOIN dim_state_sf AS st   ON c.state_id = st.state_id
JOIN dim_country_sf AS co ON st.country_id = co.country_id;
What to notice: Both designs answer the same question. The star query needs fewer joins; the snowflake stores each geographic label once and makes hierarchy maintenance safer.

3. Normalization and Denormalization

Normalization divides data into smaller related tables so each fact is stored in one logical place. It saves space, improves consistency, makes updates safer, and makes a schema easier to extend. Its cost is read complexity: normalized queries often require more joins. Denormalization reverses some separation deliberately. It is common in reporting models where simpler scans matter more than repeated descriptive values. OLTP systems generally lean toward normalization because of frequent writes; OLAP models often accept selective denormalization because they are read-heavy.

CREATE TABLE dim_country_sf (
    country_id integer PRIMARY KEY,
    country    text NOT NULL UNIQUE
);

CREATE TABLE dim_state_sf (
    state_id   integer PRIMARY KEY,
    state      text NOT NULL,
    country_id integer NOT NULL
        REFERENCES dim_country_sf(country_id),
    UNIQUE (state, country_id)
);
Common trap: Normalization is not automatically better, and denormalization is not automatically bad. A fully normalized analytical model may burden every report with joins; a heavily denormalized operational model may create inconsistent updates.

4. First, Second, and Third Normal Form

Normal forms test functional dependency. First normal form requires atomic values and no repeating groups. Second normal form requires 1NF and, when a composite key exists, every non-key attribute must depend on the whole key rather than only part of it. Third normal form requires 2NF and removes transitive dependencies: a non-key attribute must not depend on another non-key attribute. If course_id determines instructor_id and instructor_id determines instructor_name, the instructor name belongs with the instructor, not repeated in every course row.

Normal form Dependency rule Typical repair
1NF One atomic value per cell; no repeating groups. Move repeating values into separate rows or a child table.
2NF and 3NF 2NF: depend on the whole composite key. 3NF: non-key attributes depend only on the key. Split partial and transitive dependencies into entity tables connected by foreign keys.

5. Worked Example

Suppose enrollment data repeats student, course, and instructor facts in one table keyed by (student_id, course_id). Student email depends only on student_id; course title and instructor_id depend only on course_id; instructor name depends on instructor_id. The normalized design assigns each fact to its determinant.

CREATE TABLE student (
    student_id integer PRIMARY KEY,
    student_email text NOT NULL UNIQUE
);
CREATE TABLE instructor (
    instructor_id integer PRIMARY KEY,
    instructor_name text NOT NULL
);
CREATE TABLE course (
    course_id integer PRIMARY KEY,
    course_title text NOT NULL,
    instructor_id integer NOT NULL REFERENCES instructor
);
CREATE TABLE enrollment (
    student_id integer REFERENCES student,
    course_id integer REFERENCES course,
    progress numeric(5,2) CHECK (progress BETWEEN 0 AND 1),
    PRIMARY KEY (student_id, course_id)
);
Result: Each fact has one authoritative home. Updating an instructor changes one row; deleting one enrollment does not erase the course; a new course can exist before anyone enrolls.

6. Validation and Troubleshooting

  • Declare each table grain in one sentence; for enrollment, one row per student per course.
  • List candidate keys and functional dependencies before splitting tables.
  • Test update, insertion, and deletion scenarios for accidental inconsistency or information loss.
  • Compare representative star and snowflake queries with realistic data and EXPLAIN.
Red flag: A descriptive value appears in many rows with inconsistent spellings and no key, UNIQUE constraint, foreign key, or reference table to enforce one truth.

7. Common Mistakes

Normalizing without identifying the determinant Splitting a table because it looks wide is not normalization. State the dependency first, then place the fact in the table keyed by its determinant.
Assuming snowflake means faster Snowflaking reduces repeated dimension data but usually adds joins. Measure the workload before claiming a performance benefit.
Assuming a surrogate key proves normalization Adding an id column does not remove partial or transitive dependencies. A keyed table can still repeat facts incorrectly.

8. Interview Translation

What is the difference between a star and a snowflake schema? A star connects a fact table directly to wide dimensions for simpler analytical queries. A snowflake normalizes dimension hierarchies into additional tables, reducing redundancy and improving consistency at the cost of more joins.
Why normalize a database? To store each fact once, reduce redundancy, enforce integrity, and prevent update, insertion, and deletion anomalies. The trade-off is greater join complexity.
How do 2NF and 3NF differ? 2NF removes dependency on only part of a composite key. 3NF removes transitive dependency, where a non-key attribute depends on another non-key attribute.

9. Memory Review

Section summary
  1. Star means one direct dimension layer; snowflake means normalized dimension hierarchies.
  2. 1NF: atomic. 2NF: whole composite key. 3NF: no non-key-to-non-key dependency.
  3. Normalization favors integrity and safe writes; denormalization favors simpler reads.
  4. Update, insertion, and deletion anomalies signal that unrelated facts are stored together.

Quick self-check

  • Can you declare a fact-table grain before listing columns?
  • Can you explain why city, state, and country may become separate dimensions?
  • Can you find columns that depend on only part of a composite key?
  • Can you justify one deliberate denormalization choice?
