Database Management

Manage a database after its schema exists: control access with PostgreSQL roles and privileges, partition large tables for operational and analytical workloads, integrate heterogeneous data safely, and choose a DBMS whose data model and operational strengths match the business problem.

1. Big Picture

Database design does not stop when tables are created. A production database must answer four continuing questions: who may perform which actions, how growing data remains manageable, how data from different systems becomes trustworthy and comparable, and which database technology best fits the workload. These decisions connect security, performance, governance, and architecture.

Roles, Privileges, and Access Control

PostgreSQL treats users and groups as roles. Privileges such as SELECT, INSERT, UPDATE, DELETE, and object ownership should be granted to the smallest appropriate role rather than broadly to PUBLIC.

Table Partitioning

Vertical partitioning separates columns; horizontal partitioning separates rows. Partitioning is a physical organization strategy for scale and maintenance, not a substitute for normalization.

Data Integration and DBMS Selection

Data integration combines different sources, formats, and technologies into a translated, unified view. It requires explicit mappings, transformations, quality checks, security controls, and ownership.

Operational Design Trade-offs

Relational, document, key-value, and column-oriented systems optimize different access patterns. Pick from requirements, not fashion: consistency, schema stability, query style, growth, latency, and operational expertise all matter.

Section punchline: Good database management makes access intentional, growth manageable, integrated data trustworthy, and technology choices explainable.

2. Roles, Privileges, and Access Control

A PostgreSQL role is an identity that can act as a login user, a group, or both. This lets administrators separate authentication from authorization. A login role identifies a person or service; a group role represents a job function such as data_analyst. Object privileges are then granted to the group role, and users inherit those privileges through membership. This is easier to audit and maintain than repeating grants for every individual. Role attributes such as LOGIN, CREATEDB, CREATEROLE, and SUPERUSER are distinct from object privileges. Apply least privilege: grant only what the role needs, revoke obsolete access, and avoid using powerful administrator accounts for ordinary work.

-- Functional group role: no login required
CREATE ROLE data_analyst;

-- Login role for a person
CREATE ROLE sean LOGIN PASSWORD 'use-a-secret-manager';

-- Grant object access to the group
GRANT USAGE ON SCHEMA analytics TO data_analyst;
GRANT SELECT ON ALL TABLES IN SCHEMA analytics TO data_analyst;

-- Add the user to the group role
GRANT data_analyst TO sean;

-- Remove an unsafe privilege
REVOKE INSERT ON analytics.sales FROM data_analyst;

-- Change a role setting deliberately
ALTER ROLE sean SET statement_timeout = '2min';
What to notice: GRANT data_analyst TO sean grants role membership, while GRANT SELECT ON ... TO data_analyst grants an object privilege. They solve different parts of access control.

3. Table Partitioning

As tables grow into hundreds of gigabytes or terabytes, indexes may no longer fit comfortably in memory and maintenance operations become expensive. Partitioning divides one logical dataset into smaller physical pieces. Vertical partitioning moves groups of columns into separate tables linked by the same key; it is useful when wide or rarely accessed attributes should not burden common queries. Horizontal partitioning splits rows by a partition key such as date, region, tenant, or identifier range. PostgreSQL commonly uses range, list, or hash partitioning. Benefits include partition pruning, smaller indexes, easier archival, and tiered storage. Costs include more design complexity, partition maintenance, restrictions around keys, and poor performance when queries cannot filter on the partition key.

-- One logical table, physically divided by date range
CREATE TABLE orders (
    order_id      bigint,
    customer_id   bigint NOT NULL,
    ordered_at    date NOT NULL,
    amount        numeric(12,2) NOT NULL,
    PRIMARY KEY (order_id, ordered_at)
) PARTITION BY RANGE (ordered_at);

CREATE TABLE orders_2025_q1 PARTITION OF orders
FOR VALUES FROM ('2025-01-01') TO ('2025-04-01');

CREATE TABLE orders_2025_q2 PARTITION OF orders
FOR VALUES FROM ('2025-04-01') TO ('2025-07-01');

SELECT SUM(amount)
FROM orders
WHERE ordered_at >= DATE '2025-04-01'
  AND ordered_at <  DATE '2025-07-01';
Common trap: Partitioning and normalization address different problems. Normalization reduces redundancy and dependency anomalies; partitioning changes physical placement for scale and maintenance. A normalized model may still need partitioning, and a partitioned table may still be badly normalized.

4. Data Integration and DBMS Selection

Data integration creates a unified view from sources that may differ in database engine, schema, format, naming, units, identifiers, and update frequency. A robust plan defines the target model, source-to-target mappings, transformations, refresh cadence, data ownership, quality rules, lineage, failure handling, and security. Transformation tooling—often ETL or ELT—can standardize types, deduplicate records, reconcile customer identifiers, and convert currencies or time zones. The destination DBMS should then be selected from workload needs. Relational SQL systems work well when relationships, constraints, transactions, and flexible joins matter. Document stores fit evolving nested records; key-value stores fit simple high-speed lookup; column-oriented systems fit large analytical scans. “NoSQL” does not mean “no schema”—it often moves schema enforcement from the database into applications and pipelines.

Decision area Relational / SQL preference NoSQL or specialized preference
Data and consistency Stable entities, strong relationships, constraints, multi-row transactions, joins, and ACID guarantees. Rapidly evolving or nested records, simple key access, very high scale, or a specialized graph/time-series/search workload.
Query and operations Ad hoc SQL, reporting, predictable governance, mature relational tooling, and referential integrity. Known access patterns, horizontal distribution, flexible document shape, or columnar analytical throughput.

5. Worked Example

Suppose a company integrates PostgreSQL sales data, MongoDB product-behavior documents, and CSV marketing contacts into an analytical platform. The following design separates access control, staging, transformation, and consumption.

-- 1. Create functional roles
CREATE ROLE etl_writer;
CREATE ROLE reporting_reader;

-- 2. Separate ingestion from curated analytics
CREATE SCHEMA staging;
CREATE SCHEMA analytics;

GRANT USAGE, CREATE ON SCHEMA staging TO etl_writer;
GRANT USAGE ON SCHEMA analytics TO reporting_reader;

-- 3. Store raw batches by load date
CREATE TABLE staging.raw_events (
    source_system text NOT NULL,
    loaded_at     date NOT NULL,
    payload       jsonb NOT NULL
) PARTITION BY RANGE (loaded_at);

CREATE TABLE staging.raw_events_2026_01
PARTITION OF staging.raw_events
FOR VALUES FROM ('2026-01-01') TO ('2026-02-01');

-- 4. Publish a governed relational model
CREATE TABLE analytics.customer_activity (
    customer_key  bigint,
    activity_date date,
    channel       text,
    revenue       numeric(12,2),
    PRIMARY KEY (customer_key, activity_date, channel)
);

GRANT SELECT ON analytics.customer_activity TO reporting_reader;
Result: Writers can load staging data without changing curated analytics; analysts receive read-only access; raw data can be retained or removed by partition; and the unified table exposes consistent identifiers, dates, channels, and measures.

6. Validation and Troubleshooting

  • Test permissions with representative login roles: confirm allowed statements succeed and prohibited statements fail. Inspect role membership and object grants rather than assuming inheritance.
  • Use EXPLAIN to verify partition pruning. A date-filtered query should not scan every partition; missing or mis-typed predicates can defeat pruning.
  • Reconcile integrated row counts, keys, null rates, duplicate rates, units, time zones, and source totals. Record lineage from every target field back to its source and transformation.
  • Evaluate DBMS candidates against real workload tests: transaction rate, query latency, data volume, availability, recovery, security, skills, licensing, and operational burden—not only feature lists.
Red flag: A solution is unsafe when broad roles can write production data, partitions have gaps or overlaps, integration silently drops or duplicates records, or the DBMS was selected before access patterns and consistency requirements were understood.

7. Common Mistakes

Granting privileges directly to every person Create functional group roles, grant privileges to those roles, and manage users through role membership. This reduces privilege drift and makes onboarding, offboarding, and audits much clearer.
Partitioning every large-looking table Partition only when the workload and lifecycle benefit. Choose a key used by common filters and maintenance operations. Too many tiny partitions or a poor partition key adds planning and operational overhead without useful pruning.
Treating integration or NoSQL as schema-free Integrated data needs an explicit semantic model, and NoSQL data still has structure. Document mappings, contracts, validation rules, compatibility expectations, and ownership even when enforcement occurs outside the database.

8. Interview Translation

How would you implement least-privilege database access? I separate login roles from functional group roles, grant object privileges to the functional roles, and grant users membership in those roles. I avoid routine superuser use, revoke unused access, test permissions with representative accounts, and periodically review role membership and ownership.
When would you partition a table, and how would you choose the key? I partition when data volume, retention, index size, or maintenance makes one physical table difficult to manage. I choose a key aligned with frequent predicates and lifecycle operations—often time for event data—then verify pruning with actual queries. I also account for skew, uniqueness constraints, late-arriving data, and partition creation and retention.
How do you choose SQL versus NoSQL? I start from the workload: data shape, relationships, transaction and consistency requirements, query patterns, growth, latency, availability, and team capability. Relational systems are strong for integrity, transactions, and flexible joins; document, key-value, columnar, graph, or time-series systems can be better for specific shapes and access patterns. Polyglot persistence is acceptable when the operational cost is justified.

9. Memory Review

Section summary
  1. Role attributes control what an identity may be; object privileges control what it may do to database objects.
  2. Vertical partitioning splits columns; horizontal partitioning splits rows by a partition key.
  3. Integration requires a unified semantic model plus mappings, quality checks, lineage, security, and failure handling.
  4. Choose a DBMS from workload and operational requirements—not from popularity or the label SQL/NoSQL.

Quick self-check

  • Can you explain the difference between a login role, a group role, role membership, and an object privilege?
  • Can you distinguish partitioning from normalization and give one useful partition key?
  • Can you list the minimum controls in a trustworthy data-integration plan?
  • Can you defend a relational, document, key-value, or columnar choice using concrete access patterns?
Lab decision: A focused PostgreSQL lab is worthwhile: create login and group roles, prove GRANT/REVOKE behavior, build a range-partitioned event table, inspect pruning with EXPLAIN, and document a source-to-target mapping for a small integration.
Completion standard: Complete this chapter when you can design role-based access, explain and implement vertical versus horizontal partitioning, review an integration plan for quality and security gaps, and justify a DBMS choice with workload-specific trade-offs.
