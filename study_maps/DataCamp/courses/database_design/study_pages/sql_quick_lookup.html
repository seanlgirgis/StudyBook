Workloads and Storage

Operational database

Runs current business transactions.

Operational tables + PK/FK + short transactions
Operational describes purpose; OLTP describes the common processing pattern.

OLTP

Many short concurrent reads/writes.

BEGIN; INSERT ...; UPDATE ...; COMMIT;
Keep transactions short and enforce integrity.

OLAP

Large scans, joins, and aggregates.

SELECT dim, SUM(measure) ... GROUP BY dim;
Do not force heavy analytics onto a latency-sensitive OLTP system.

Modeling and Normalization

Fact-table grain

Defines what one fact row means.

One row per order line
Never mix measures at different grains.

Star schema

Fact table joined to denormalized dimensions.

fact_sales → dim_date, dim_product, dim_customer
Simpler joins can mean repeated dimension attributes.

Snowflake schema

Normalizes dimension hierarchies.

dim_product → dim_category
More normalization means more joins.

Views and Access

1NF

Atomic values and no repeating groups.

one value per column per row
Atomic is defined by the data model and intended operations.

2NF

No partial dependency on part of a composite key.

(student_id, course_id) → grade
Only relevant when a candidate key has multiple attributes.

3NF

No transitive non-key dependency.

employee_id → dept_id; dept_id → dept_name
Move department facts to a department relation.

Scale, Integration, and Selection

Regular view

Stored query evaluated when used.

CREATE VIEW v AS SELECT ...;
A regular view normally stores no result rows.

Materialized view

Stored result refreshed explicitly.

REFRESH MATERIALIZED VIEW mv;
Fast can mean stale; define refresh ownership.

Role privilege

Groups or assigns allowed actions.

GRANT SELECT ON t TO analyst_role;
Grant the minimum needed and test effective membership.

Database Design Decision Flow

Need current transactions? Yes → OLTP / operational design → normalize and constrain No → Need large historical analysis? Yes → OLAP / dimensional design Repeated expensive query? → consider materialized view Very large table with aligned filters? → consider partitioning Choose DBMS only after workload and operational constraints are clear.
Start with the workload and business rules. Every optimization creates a responsibility: duplicated data needs synchronization, materialized data needs refresh, partitions need lifecycle management, and privileges need review.
