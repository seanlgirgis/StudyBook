2. Course Big Picture

Database design starts with workload and business rules, not with table syntax. Operational databases protect current transactions; analytical systems reorganize history for large scans and aggregation. Schemas, views, permissions, partitioning, and integration are design decisions that trade write simplicity, read speed, consistency, freshness, and maintainability.

Business questions and service needs | v Choose workload: OLTP / OLAP / mixed | v Model data: normalized entities or dimensional facts + dimensions | v Expose safely: views, materialized views, roles, privileges | v Operate at scale: partitions, integration pipelines, DBMS choice
Course punchline: Design from workload, grain, dependencies, and access patterns; then prove integrity, performance, freshness, and security.

3. Core Concepts

Operational database

Runs day-to-day activity with current detailed data, frequent small transactions, concurrency, and strong integrity.

Analytical database

Supports history, aggregation, reporting, and scans across large volumes; commonly modeled for OLAP.

Normalization

Stores each fact in the appropriate place to reduce redundancy and prevent update, insertion, and deletion anomalies.

Dimensional modeling

Defines a fact-table grain and descriptive dimensions to make analytical questions easy and predictable.

Views

Provide reusable query interfaces; materialized views trade storage and refresh work for faster reads.

Operational governance

Roles, privileges, partitions, integration controls, and DBMS selection keep the design secure and sustainable.

4. Core Syntax and Patterns

Normalized operational core

CREATE TABLE customer (
  customer_id bigint PRIMARY KEY,
  customer_name text NOT NULL
);

CREATE TABLE orders (
  order_id bigint PRIMARY KEY,
  customer_id bigint NOT NULL REFERENCES customer(customer_id),
  ordered_at timestamptz NOT NULL
);

Separate entities, identify keys, and enforce relationships. This reduces duplication while preserving transaction integrity.

Analytical star schema

fact_sales(
  date_key,
  customer_key,
  product_key,
  quantity,
  revenue
)

dim_date(...)
dim_customer(...)
dim_product(...)

State the fact grain first—for example one row per sold product per order—then attach dimensions at compatible grain.

Managed read interface

CREATE VIEW reporting.order_summary AS
SELECT customer_id, count(*) AS order_count
FROM orders
GROUP BY customer_id;

GRANT SELECT ON reporting.order_summary TO analyst_role;

A view centralizes logic and narrows access, but it does not automatically materialize data or eliminate dependency management.

5. Comparisons and Decision Rules

Normalize for write correctness

Best when many transactions update shared business entities and consistency matters more than one-query simplicity.

Denormalize for read efficiency

Useful when repeated joins dominate analytical workloads and duplication can be controlled through reliable pipelines.

Decision Prefer Reason
Frequent inserts and updates Normalized OLTP schema Reduces duplicate facts and anomalies.
Repeated aggregate reporting Star schema or materialized view Makes scans and joins simpler or precomputes expensive work.
Very large time-based table Range partitioning Can prune irrelevant partitions and simplify retention operations.

6. Common Mistakes

Starting with tables before requirements Define users, transactions, questions, volume, latency, freshness, and integrity rules first.
Confusing OLTP with operational reporting An operational database serves current transactions; reporting against it is a workload imposed on that system, not a reason to call it OLAP.
Normalizing without checking dependencies Normal forms are driven by keys and functional dependencies, not by merely creating more tables.
Treating materialized views as automatically fresh They store results and require a refresh strategy, dependency order, monitoring, and acceptable staleness.

7. Interview Translation

What is an operational database? It supports current day-to-day transactions such as orders, payments, and inventory updates. It is usually OLTP-oriented: many short concurrent operations, strong integrity, and low-latency reads and writes.
When would you normalize a schema? When duplicate facts create integrity risk and the workload has frequent inserts or updates. I identify candidate keys and functional dependencies, then decompose while preserving relationships.
How do star and snowflake schemas differ? A star keeps dimensions relatively denormalized for simpler analytical joins; a snowflake normalizes dimension hierarchies, reducing some duplication but increasing joins and complexity.
How do you choose a DBMS? I start with workload, consistency, query shape, data model, scale, latency, operations, ecosystem, and team capability—then test the riskiest assumptions with representative data.

9. Quick Memory Nuggets

Operational = operate now
Analytical  = understand history
OLTP        = many short transactions
OLAP        = scans, joins, aggregates
Normalization question:
What does each non-key attribute depend on?
Star-schema question:
What exactly does one fact row represent?
View = stored query
Materialized view = stored result
Partition = physical table subdivision
Role = privilege container / login identity
Final review: Be able to explain each design as a trade-off. Avoid absolute claims such as “normalized is always better” or “NoSQL is faster.”
