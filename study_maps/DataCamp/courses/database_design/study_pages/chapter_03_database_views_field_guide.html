1. Big Picture

A view gives a name to a query so users can query its result as though it were a table. A regular view stores the query definition, not a separate copy of the result. This makes views useful for simplifying complex joins, presenting a stable interface over changing tables, and limiting which rows or columns users can see. A materialized view is different: it stores the query result physically and must be refreshed when the underlying data changes.

Base tables | | CREATE VIEW ... AS SELECT ... v Regular view (query definition stored; result computed when queried) | +--> simpler interface +--> reusable business logic +--> access boundary Base tables | | CREATE MATERIALIZED VIEW ... AS SELECT ... v Materialized view (result stored physically; refreshed deliberately) | +--> faster reads +--> storage cost +--> possible staleness

Regular Views: Stored Queries as Interfaces

A regular view is a virtual table backed by a stored SELECT statement. It is queried like a table, but its rows are normally derived at query time.

Managing, Securing, and Redefining Views

Views can be granted or revoked from roles, may sometimes support INSERT or UPDATE, and can be replaced or dropped with dependency-aware commands.

Materialized Views and Refresh Strategy

A materialized view stores result rows, making repeated expensive reads faster at the cost of storage and data freshness.

View Dependencies

Views may depend on tables or other views. Those dependencies affect replacement, dropping, refresh order, and pipeline scheduling.

Section punchline: Use a regular view to package and protect query logic; use a materialized view when repeated query cost matters more than immediate freshness.

2. Regular Views: Stored Queries as Interfaces

A regular view behaves like a table from the consumer's perspective, but PostgreSQL stores the defining query rather than a separate data copy. Each query against the view expands into the underlying query plan. This lets a team hide normalized joins, expose only approved columns, and keep reporting SQL stable even when the physical schema is more complex.

CREATE VIEW sci_fi_books AS
SELECT
    b.title,
    a.author
FROM dim_book_sf AS b
JOIN dim_author_sf AS a
  ON b.author_id = a.author_id
JOIN dim_genre_sf AS g
  ON b.genre_id = g.genre_id
WHERE g.genre = 'science fiction';

SELECT *
FROM sci_fi_books;

-- Inspect views available through the information schema
SELECT table_schema, table_name
FROM information_schema.views
WHERE table_schema NOT IN ('pg_catalog', 'information_schema');
What to notice: The view exposes only the columns and rows selected by its defining query. The underlying tables remain the source of truth, and the view normally consumes no separate row-storage space.

3. Managing, Securing, and Redefining Views

A view is also a database object with privileges and dependencies. PostgreSQL can grant SELECT, INSERT, UPDATE, or DELETE privileges on a view, although a privilege does not guarantee that the view is structurally updatable. Simple single-table views are more likely to be automatically updatable; joins, aggregation, DISTINCT, set operations, and grouping commonly make a view read-only unless additional mechanisms are provided.

-- Give analysts read access without exposing the base table directly
GRANT SELECT ON sci_fi_books TO analyst_role;

-- Remove a privilege
REVOKE UPDATE ON sci_fi_books FROM analyst_role;

-- Replace the defining query
CREATE OR REPLACE VIEW sci_fi_books AS
SELECT
    b.book_id,
    b.title,
    a.author
FROM dim_book_sf AS b
JOIN dim_author_sf AS a
  ON b.author_id = a.author_id
JOIN dim_genre_sf AS g
  ON b.genre_id = g.genre_id
WHERE g.genre = 'science fiction';

-- Drop only when nothing depends on the view
DROP VIEW sci_fi_books RESTRICT;
Common trap: GRANT UPDATE does not make a complex view updatable. Privilege checks and structural updatability are separate questions. Also, CREATE OR REPLACE VIEW must preserve compatible existing columns; renaming or removing columns may require a controlled drop-and-recreate.

4. Materialized Views and Refresh Strategy

Materialized views physically store the output of a query. Queries read those stored rows instead of rerunning the full underlying query. They are well suited to expensive aggregations, warehouse workloads, and data that changes less frequently than it is read. Their central design decision is refresh policy: how stale may the data be, how long does refresh take, and what depends on the result?

Feature Regular view Materialized view
What is stored The query definition The query result rows
Freshness and cost Current base data, but query work happens at read time Fast reads, but results can become stale until refreshed

5. Worked Example

Suppose an analytics team repeatedly calculates monthly sales by region from a large fact table. A regular view centralizes the business logic, while a materialized view can cache the expensive aggregate for dashboards.

CREATE MATERIALIZED VIEW monthly_region_sales AS
SELECT
    date_trunc('month', sold_at) AS sales_month,
    region_id,
    SUM(amount) AS total_sales,
    COUNT(*) AS order_count
FROM sales
GROUP BY
    date_trunc('month', sold_at),
    region_id;

CREATE INDEX monthly_region_sales_idx
    ON monthly_region_sales (sales_month, region_id);

-- Recompute stored results after source data changes
REFRESH MATERIALIZED VIEW monthly_region_sales;

SELECT *
FROM monthly_region_sales
WHERE sales_month = DATE '2026-05-01';
Result: Dashboard queries scan the compact, pre-aggregated result instead of recomputing the full sales aggregation each time. The trade-off is that the dashboard reflects the last successful refresh, not necessarily the latest transaction.

6. Validation and Troubleshooting

  • Query the view and compare representative rows with the equivalent base-table query.
  • Check the exposed columns and privileges to confirm that sensitive fields are not reachable through the view.
  • Before replacing or dropping a view, identify dependent views, reports, functions, and scheduled jobs.
  • For materialized views, record the last refresh time and test whether refresh duration fits the allowed maintenance window.
Red flag: A report silently relies on stale materialized data, or a DROP ... CASCADE removes dependent objects that were not reviewed.

7. Common Mistakes

Treating a view as an independent data copy A regular view usually stores only its query definition. Changes in base data are visible when the view is queried, subject to transaction visibility.
Assuming every view is writable Updatability depends on the defining query. Joins and aggregations commonly prevent automatic INSERT, UPDATE, or DELETE operations.
Using materialized views without a freshness contract Define who refreshes the view, how often, how failures are detected, and how much staleness consumers can tolerate.

8. Interview Translation

What is the difference between a table and a view? A table stores rows physically. A regular view stores a query definition and presents its result as a virtual table. It is useful for abstraction, reuse, and access control, but its query cost is generally paid when the view is read.
When would you choose a materialized view? I would choose one for expensive, repeatedly read queries where some staleness is acceptable, such as warehouse aggregates or dashboard summaries. I would also define an explicit refresh and dependency strategy.
How can views improve security? A view can expose an approved subset of columns or rows while permissions on the base tables remain restricted. It is an interface layer, not a replacement for correct role, ownership, and privilege design.

9. Memory Review

Section summary
  1. Regular view: store the query, compute the result when read.
  2. Materialized view: store the result, refresh it when needed.
  3. Privileges do not guarantee structural updatability.
  4. Dependencies must be understood before replace, drop, or refresh operations.

Quick self-check

  • Can you explain why a regular view normally shows current base-table data?
  • Can you name two query features that often make a view non-updatable?
  • Can you describe the speed-versus-freshness trade-off of a materialized view?
  • Can you explain the difference between DROP VIEW RESTRICT and CASCADE?
Lab decision: A focused PostgreSQL lab is valuable: create a normal view, grant restricted access, test an updatable and non-updatable view, then create and refresh a materialized aggregate.
Completion standard: You can create, query, inspect, secure, replace, and drop views safely; distinguish regular from materialized views; and explain refresh and dependency trade-offs without overclaiming that every view is writable.
