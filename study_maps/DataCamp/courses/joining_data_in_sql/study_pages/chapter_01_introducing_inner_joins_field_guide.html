1. Big Picture

A join combines related rows at query time. It does not permanently merge tables. The database evaluates a relationship between columns and returns the requested fields from the matching rows.

Choose the starting table ↓ Identify the related table ↓ Choose the matching key or keys ↓ Join the rows ↓ Select and validate the result

INNER JOIN

Keeps rows only when the join condition finds a match in both inputs.

Primary key

Uniquely identifies a row in its own table.

Foreign key

Refers to a key in another table and creates a relationship.

Cardinality

Determines whether one key produces one row or many output rows.

Chapter punchline: a correct join starts with the real-world relationship, not merely with columns that have the same data type.

2. The Ins and Outs of INNER JOIN

For each row in one table, SQL searches the other table for rows that satisfy the join condition. Only successful matches remain.

countries populations --------- ----------- code name country_code year population USA United States USA 2020 331000000 CAN Canada CAN 2020 38000000 MEX Mexico BRA 2020 213000000 INNER JOIN on countries.code = populations.country_code USA and CAN remain. MEX has no population match and is removed. BRA has no country match and is removed.
Important: an INNER JOIN may return more rows than either source table when one key matches several rows. That is normal in one-to-many relationships.

3. Your First Join

SELECT c.name,
       p.year,
       p.population
FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code;

Read the query in plain English

  1. Start with the countries table.
  2. Match rows from populations.
  3. Use country code as the relationship.
  4. Keep only matching rows.
  5. Return country name, year, and population.
Join condition rule: compare fields that represent the same real-world identifier. Similar names or matching data types are not enough.

4. Joining with Aliased Tables

Aliases shorten references and make column ownership explicit. 

SELECT c.name,
       p.year,
       p.population
FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code;
Practice Why it matters
countries AS c Creates a short, readable table reference.
c.name Shows exactly which table supplies the field.
Use aliases consistently Prevents ambiguity in SELECT, ON, WHERE, and ORDER BY.
Common mistake: after assigning an alias, do not keep using the original table name in the same query block. Use the alias consistently.

5. ON versus USING

Use ON

FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code

Use it when field names differ or the relationship needs several conditions.

Use USING

FROM countries AS c
INNER JOIN economies AS e
  USING (code)

Use it when both tables have the same join-column name.

Feature ON USING
Different field names Supported Not supported
Compound conditions Supported Only shared named fields
Readability More explicit More compact
Join key in output Both field versions may remain addressable Usually exposed as one merged key field
Memory rule: same field name on both sides means USING is possible. Different names require ON.

6. Defining Table Relationships

Primary key

A field or field set that uniquely identifies one row.

Example: countries.code.

Foreign key

A field whose values refer to a key in another table.

Example: populations.country_code.

Common relationship shapes

Relationship Meaning Typical result effect
One-to-one One row on each side for a key Usually one result row per match
One-to-many One parent row matches several child rows Parent values repeat across result rows
Many-to-many Several rows on both sides share a key Rows may multiply rapidly
Key lesson: join keys do not have to be unique, but their uniqueness determines how many output rows are produced.

7. Inspecting a Relationship

Before trusting a join, inspect the fields and sample values that connect the tables.

Inspect key values

SELECT code,
       name
FROM countries
ORDER BY code;

SELECT country_code,
       year,
       population
FROM populations
ORDER BY country_code,
         year;

Check key frequency

SELECT country_code,
       COUNT(*) AS rows_per_country
FROM populations
GROUP BY country_code
ORDER BY rows_per_country DESC;

This reveals whether each country appears once or many times in the child table.

Before joining: confirm meaning, data type, sample values, nullability, uniqueness, and whether an additional field such as year is part of the relationship.

8. Joining Multiple Tables

Add tables one at a time. Each new join should connect to tables already available in the query through a valid relationship. 

SELECT c.name,
       p.year,
       p.fertility_rate,
       e.unemployment_rate
FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code
INNER JOIN economies AS e
  ON c.code = e.code
 AND p.year = e.year;
Why match both country and year? Country identifies the entity, while year identifies the reporting period. Omitting year may combine unrelated periods.

Build the join incrementally

-- Step 1: validate countries and populations
SELECT c.code,
       c.name,
       p.year
FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code;

-- Step 2: add economies with the complete relationship
SELECT c.code,
       c.name,
       p.year,
       e.unemployment_rate
FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code
INNER JOIN economies AS e
  ON c.code = e.code
 AND p.year = e.year;

9. Checking Multi-Table Joins

A query may execute successfully while still being logically wrong. Validate each stage of the join.

  • Compare row counts before and after each join.
  • Select the join keys temporarily so you can inspect them.
  • Check whether duplicate growth is expected.
  • Include time or another dimension when the relationship requires it.
  • Build one join at a time instead of writing the entire chain at once.
SELECT c.code,
       p.year,
       COUNT(*) AS joined_rows
FROM countries AS c
INNER JOIN populations AS p
  ON c.code = p.country_code
INNER JOIN economies AS e
  ON c.code = e.code
 AND p.year = e.year
GROUP BY c.code,
         p.year
HAVING COUNT(*) > 1;
Red flag: when a result becomes much larger than expected, inspect whether part of a composite relationship—such as year—was omitted.

10. Common Mistakes

Joining fields only because their names look related Similar names do not prove that the fields represent the same business key.
Ignoring year in a country-and-year relationship This may create cross-year combinations for each country.
Selecting an ambiguous field name Use the table alias, such as c.name, when several tables contain fields with the same name.
Expecting unmatched rows from INNER JOIN INNER JOIN removes rows that do not satisfy the join condition.
Assuming one match per key One-to-many relationships legitimately repeat the parent row.
Writing every join before testing Build the query in stages so row growth and faulty conditions are easier to find.

11. Interview Translation

What does INNER JOIN do? It returns rows where the join condition finds a match in both inputs. Unmatched rows from either side are excluded.
Why can an INNER JOIN increase row count? Because one key may match several rows. In one-to-many or many-to-many relationships, each valid combination becomes an output row.
When would you use USING instead of ON? I use USING when both tables share the same join-field name and the relationship is simple. I use ON for different names, compound keys, or more explicit conditions.
How do you troubleshoot a multi-table join? I add one join at a time, inspect the key fields, compare row counts, test key uniqueness, and verify that every part of a composite key is included.
What is the difference between a primary key and a foreign key? A primary key uniquely identifies a row in its own table. A foreign key stores values that refer to a key in another table.

12. Memory Review

Six-sentence chapter summary
  1. INNER JOIN keeps matched rows only.
  2. Aliases make field ownership clear.
  3. USING requires matching field names.
  4. Primary and foreign keys describe how tables relate.
  5. Relationship cardinality determines row multiplication.
  6. Multi-table joins may require compound conditions such as entity plus year.
