Subqueries

Use semi joins and anti joins to test membership, place nested queries inside WHERE, SELECT, and FROM, and choose the correct subquery shape for filtering, comparison, summary, and diagnostics.

1. Big Picture

A subquery is a query nested inside another query. The inner query produces a value, a list, an existence test, or a temporary result set that the outer query uses.

Outer query ↓ Needs a value, list, existence test, or temporary table ↓ Inner query produces it ↓ Outer query filters, compares, or summarizes

Inside WHERE

Filter rows using a value, list, or existence test.

Inside SELECT

Return one derived value beside each outer row.

Inside FROM

Treat an intermediate query result as a table.

Semi / anti join

Keep rows based on whether a related row exists.

Chapter punchline: a subquery answers a smaller question whose result becomes input to a larger question.

2. Semi Joins

A semi join keeps rows from the first table when at least one related row exists in another table. It returns only fields from the outer table.

Using IN

SELECT name
FROM countries
WHERE code IN (
  SELECT country_code
  FROM economies
);

Using EXISTS

SELECT c.name
FROM countries AS c
WHERE EXISTS (
  SELECT 1
  FROM economies AS e
  WHERE e.country_code = c.code
);
Use a semi join when: you need to test whether a relationship exists, but you do not need fields from the related table.

3. Anti Joins

An anti join keeps rows from the first table when no related row exists in the second.

Using NOT EXISTS

SELECT c.name
FROM countries AS c
WHERE NOT EXISTS (
  SELECT 1
  FROM economies AS e
  WHERE e.country_code = c.code
);

Using LEFT JOIN and IS NULL

SELECT c.name
FROM countries AS c
LEFT JOIN economies AS e
  ON c.code = e.country_code
WHERE e.country_code IS NULL;
Preferred defensive pattern: NOT EXISTS is safer than NOT IN when the inner result may contain NULL.
NULL trap: one NULL in a NOT IN subquery can make comparisons unknown and produce an unexpected empty result.

4. Subqueries inside WHERE

A subquery in WHERE commonly returns one value, a list of values, or an existence result.

Compare against one value

SELECT name,
       population
FROM cities
WHERE population > (
  SELECT AVG(population)
  FROM cities
);

Filter by a list

SELECT name
FROM countries
WHERE code IN (
  SELECT country_code
  FROM languages
  WHERE language = 'French'
);
Shape rule: use =, >, or similar operators when the inner query returns one value. Use IN when it returns many values.

5. IN, EXISTS, and Membership Tests

PatternBest useMain caution
IN (subquery)Compare a value to a returned listBe careful with NOT IN and NULL
EXISTS (subquery)Test whether at least one related row existsUsually needs a correct correlation condition
NOT EXISTSFind rows without a related matchConfirm the relationship inside the inner WHERE
 
SELECT c.name
FROM countries AS c
WHERE EXISTS (
  SELECT 1
  FROM languages AS l
  WHERE l.country_code = c.code
    AND l.official = TRUE
);

The SELECT 1 emphasizes that only existence matters; no inner field is returned to the outer result.

Memory rule: use IN for list membership and EXISTS for existence of a related row.

6. Subqueries inside SELECT

A subquery in SELECT must produce one value for each outer row.

Uncorrelated scalar subquery

SELECT name,
       population,
       (
         SELECT AVG(population)
         FROM cities
       ) AS average_city_population
FROM cities;

The same overall average appears beside every city.

Correlated scalar subquery

SELECT c.name,
       (
         SELECT COUNT(*)
         FROM cities AS ci
         WHERE ci.country_code = c.code
       ) AS city_count
FROM countries AS c;
Correlated subqueries in SELECT are readable, but a grouped join may be more efficient for large datasets.

7. Subqueries inside FROM

A subquery in FROM creates an intermediate result that the outer query can treat like a table.

SELECT region,
       AVG(country_population) AS average_population
FROM (
  SELECT region,
         code,
         population AS country_population
  FROM countries
  WHERE population IS NOT NULL
) AS country_data
GROUP BY region;

Good reasons to use one

  • Break a complex question into stages.
  • Aggregate once, then aggregate again.
  • Rename or filter fields before later calculations.
  • Create a clear intermediate dataset for the outer query.
PostgreSQL rule: a subquery in FROM needs an alias.

8. Correlated Subqueries

A correlated subquery references a field from the outer query and therefore depends on the current outer row.

SELECT c.name
FROM countries AS c
WHERE EXISTS (
  SELECT 1
  FROM cities AS ci
  WHERE ci.country_code = c.code
    AND ci.population > 1000000
);
Outer row: one country ↓ Inner query checks cities for that country ↓ EXISTS returns TRUE or FALSE ↓ Outer country is kept or discarded
Common error: forgetting ci.country_code = c.code turns the inner query into a global test instead of a row-specific test.

9. Scalar, Multi-Row, Table, and Existence Shapes

ShapeReturnsTypical use
ScalarOne row and one value=, >, SELECT expression
Single-column multi-rowSeveral valuesIN
Table subquerySeveral rows and fieldsFROM
Existence subqueryTRUE/FALSE existence testEXISTS, NOT EXISTS

Wrong operator for a multi-row result

SELECT name
FROM countries
WHERE code = (
  SELECT country_code
  FROM cities
);

If several country codes are returned, = fails. Use IN or reduce the inner query to one row.

Before writing the outer query: determine the exact shape returned by the inner query.

10. Choosing the Right Pattern

QuestionPatternReason
Which countries have economy rows?IN or EXISTSSemi-join membership test
Which countries lack economy rows?NOT EXISTSAnti-join pattern
Which cities exceed the overall average?Scalar subquery in WHERECompare each row with one summary value
Show each country with a city countScalar correlated subquery in SELECTReturn one derived value per outer row
Aggregate an intermediate resultSubquery in FROMCreate a staged temporary table
Decision shortcut: filter by list → IN; test existence → EXISTS; compare with one value → scalar subquery; stage a table → subquery in FROM.

11. Common Mistakes

Using = when the subquery returns many rowsUse IN, EXISTS, or aggregate the inner query to one value.
Using NOT IN when NULL may appearPrefer NOT EXISTS for NULL-safe anti-join logic.
Forgetting the alias on a FROM subqueryPostgreSQL requires a derived-table alias.
Returning several fields in a scalar contextA scalar subquery must return one field and at most one row.
Forgetting the correlation conditionThe result may become global instead of row-specific.
Using a correlated subquery when a join is clearerRepeated row-by-row logic can be harder to maintain and may perform worse.
Assuming subqueries are always faster than joinsPerformance depends on indexes, data size, optimizer behavior, and query shape.

12. Interview Translation

What is a subquery?A SELECT statement nested inside another SQL statement whose result becomes input to the outer query.
What is a semi join?It returns rows from the first table when a related row exists, without returning fields from the second table.
What is an anti join?It returns rows from the first table when no related row exists in the second.
What is a correlated subquery?A subquery that references the outer query and is evaluated logically in the context of each outer row.
Why is NOT EXISTS safer than NOT IN?NOT IN can fail logically when NULL appears in the inner result, while NOT EXISTS checks for matching rows directly.
When do you use a FROM subquery?When a problem benefits from staged filtering, renaming, or aggregation before the final query.
How do you choose between a join and a subquery?Use a join when fields from both sides are needed; use semi/anti subqueries for existence tests and scalar/FROM subqueries for staged calculations.

13. Memory Review

Seven-sentence chapter summary
  1. A subquery is nested SQL used by an outer query.
  2. Semi joins keep rows when a related row exists.
  3. Anti joins keep rows when no related row exists.
  4. WHERE subqueries filter by values, lists, or existence.
  5. SELECT subqueries must return one value per outer row.
  6. FROM subqueries act as temporary tables and need aliases.
  7. Correlated subqueries depend on fields from the outer query.
