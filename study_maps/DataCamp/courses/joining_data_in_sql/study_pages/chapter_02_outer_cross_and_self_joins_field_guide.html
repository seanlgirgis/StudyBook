Outer Joins, Cross Joins and Self Joins

1. Big Picture

Chapter 1 focused on matched rows. Chapter 2 asks a broader question: which rows must remain when a match does not exist?

Start with the business population ↓ Decide which unmatched rows must remain ↓ Choose INNER, LEFT, RIGHT, or FULL JOIN ↓ Check whether rows may multiply ↓ Validate NULLs and row counts

Outer joins

Preserve unmatched rows from one side or from both sides.

CROSS JOIN

Create every possible combination without a join condition.

Self join

Use one physical table twice under different aliases and roles.

Core decision

Choose joins by required row preservation, not by table size.

Chapter punchline: join selection is fundamentally a row-preservation decision.

2. LEFT JOIN and RIGHT JOIN

A LEFT JOIN keeps every row from the table written before the join. A RIGHT JOIN keeps every row from the table written after the join.

LEFT JOIN

SELECT c.code,
       c.name,
       e.year,
       e.gdp_percapita
FROM countries AS c
LEFT JOIN economies AS e
  ON c.code = e.code;

Every country survives. If a country has no matching economy row, the economy columns contain NULL.

RIGHT JOIN

SELECT c.code,
       c.name,
       e.year,
       e.gdp_percapita
FROM countries AS c
RIGHT JOIN economies AS e
  ON c.code = e.code;

Every economy row survives. Country columns become NULL when no matching country exists.

Practical preference: many teams rewrite RIGHT JOIN as LEFT JOIN by swapping table order because the preserved population is easier to read from the FROM clause.

3. Remembering What Is LEFT

FROM countries AS c ← left table LEFT JOIN economies AS e ← right table ON c.code = e.code

“Left” refers only to the table's position in the query. It does not mean:

  • the larger table,
  • the parent table,
  • the table with the primary key, or
  • the first table created in the database.
Question Answer
Which rows must survive? Every row from countries.
Where do missing values appear? In columns selected from economies.
Can one country appear more than once? Yes, when it matches several economy rows.
Does LEFT JOIN preserve the exact left row count? No. It preserves every left row, but one-to-many matches can increase the result count.
Common misconception: LEFT JOIN does not guarantee exactly one output row per left row.

4. Filter Placement: ON versus WHERE

A right-table filter placed in WHERE can remove the unmatched rows that a LEFT JOIN was supposed to preserve.

WHERE removes unmatched rows

SELECT c.name,
       e.year,
       e.gdp_percapita
FROM countries AS c
LEFT JOIN economies AS e
  ON c.code = e.code
WHERE e.year = 2015;

Unmatched rows have e.year = NULL. The WHERE condition rejects them.

ON limits eligible matches but preserves countries

SELECT c.name,
       e.year,
       e.gdp_percapita
FROM countries AS c
LEFT JOIN economies AS e
  ON c.code = e.code
 AND e.year = 2015;
Decision rule: put a right-side condition in ON when it defines which rows may match. Put it in WHERE when you intentionally want to filter the final result.

5. FULL JOIN

A FULL JOIN returns matched rows, unmatched left rows, and unmatched right rows. 

SELECT c.code AS country_code,
       c.name,
       e.code AS economy_code,
       e.year,
       e.gdp_percapita
FROM countries AS c
FULL JOIN economies AS e
  ON c.code = e.code;
countries.code economies.code Result -------------- -------------- ------------------------ USA USA matched row CAN NULL left-only row NULL BRA right-only row

Good uses for FULL JOIN

  • reconciling records from two systems,
  • finding keys missing from either side,
  • migration validation,
  • data-quality comparison, and
  • building a complete combined key universe.
Memory rule: FULL JOIN means, “show everything from both sides and align matches where possible.”

6. Comparing the Main Join Types

Join Matched rows Unmatched left Unmatched right Typical question
INNER JOIN Yes No No Which records exist in both tables?
LEFT JOIN Yes Yes No Show all customers, including those without orders.
RIGHT JOIN Yes No Yes Show every right-side record, even without a left match.
FULL JOIN Yes Yes Yes Reconcile two complete systems.
CROSS JOIN Not key-based Not applicable Not applicable Generate every possible combination.

7. Chaining FULL JOINs

After the first FULL JOIN, the usable key may exist on either side. COALESCE can choose the first non-NULL key for the next join. 

SELECT COALESCE(c.code, e.code, p.country_code) AS country_code,
       c.name,
       e.year AS economy_year,
       p.year AS population_year
FROM countries AS c
FULL JOIN economies AS e
  ON c.code = e.code
FULL JOIN populations AS p
  ON COALESCE(c.code, e.code) = p.country_code;
Why COALESCE helps: a row preserved only from economies has c.code = NULL but may still have a valid e.code.
Chained FULL JOINs can be difficult to reason about when keys are duplicated. Validate each two-table stage before adding the next join.

8. CROSS JOIN

CROSS JOIN has no join condition. Every row from the first source is paired with every row from the second. 

SELECT c.name,
       l.name AS language
FROM countries AS c
CROSS JOIN languages AS l;
3 country rows × 4 language rows = 12 result rows

Useful CROSS JOIN cases

  • products × reporting months,
  • regions × planning scenarios,
  • students × required assessments,
  • test parameters × test values,
  • creating a complete reporting grid before attaching actual facts.

Controlled reporting grid

SELECT c.code,
       c.name,
       y.year
FROM countries AS c
CROSS JOIN (
  VALUES (2023),
         (2024),
         (2025)
) AS y(year);
Explosion risk: output rows equal left rows multiplied by right rows. One million rows crossed with one thousand rows creates one billion rows.

9. Self Joins

A self join uses the same physical table more than once under different aliases. Each alias represents a different role, level, or time period.

Compare two years for the same country

SELECT p1.country_code,
       p1.year AS start_year,
       p1.population AS start_population,
       p2.year AS end_year,
       p2.population AS end_population,
       p2.population - p1.population AS population_change
FROM populations AS p1
INNER JOIN populations AS p2
  ON p1.country_code = p2.country_code
 AND p1.year = 2010
 AND p2.year = 2015;

Employee-to-manager hierarchy

SELECT employee.name AS employee_name,
       manager.name AS manager_name
FROM employees AS employee
LEFT JOIN employees AS manager
  ON employee.manager_id = manager.employee_id;

Alias 1

Represents the employee, earlier period, child row, or first comparison role.

Alias 2

Represents the manager, later period, parent row, or second comparison role.

A broad self join may produce A–A, A–B, and B–A. Use a condition such as a.id < b.id when each unordered pair should appear only once.

10. Choosing the Join

Business requirement Likely join Reason
Only customers who placed an order INNER JOIN Only matches are required.
All customers, including those with no orders LEFT JOIN The customer population must be preserved.
All records from two systems, including unmatched keys FULL JOIN Both complete populations must survive.
Every product for every reporting month CROSS JOIN A complete combination grid is intentional.
Employee and manager from one employee table Self LEFT JOIN The same table plays two roles, and top-level managers may have no parent.
Compare one country's values across two years Self INNER JOIN Two rows from one table are paired by country.
Best sequence: identify the main population → decide which unmatched rows must remain → confirm key cardinality → estimate row multiplication → choose the join.

11. Common Mistakes

Assuming LEFT means the parent or larger table LEFT is determined only by the table's position after FROM.
Filtering the right table in WHERE unintentionally The filter removes NULL-extended rows and can create inner-join behavior.
Expecting one output row per left row One-to-many matches can duplicate left-side values.
Running CROSS JOIN without estimating size Row counts multiply rather than add.
Self joining without aliases Column references become ambiguous and the two roles are unclear.
Self joining only on the entity key This may create every time-period combination for each entity.
Chaining FULL JOINs on one nullable key Rows preserved from the other side may fail to match the third table.

12. Interview Translation

How do you choose between INNER JOIN and LEFT JOIN? I begin with the required output population. If unmatched rows should be excluded, I use an inner join. If every row from the primary population must remain, I use a left join and expect NULL values for missing right-side data.
What is a common LEFT JOIN bug? Filtering a right-side field in the WHERE clause can remove NULL-extended rows. When the condition defines which right-side rows may match, I place it in ON.
When would you use FULL JOIN? I use it mainly for reconciliation and completeness analysis, where I need matched records plus keys missing from either system.
What is the risk of CROSS JOIN? Its row count grows multiplicatively. I estimate the expected size first and use it only when every combination is intentional.
What is a self join? It is a normal join where the same physical table appears under separate aliases so each instance can represent a different role, hierarchy level, or time period.
How do you validate an outer join? I compare source and result counts, inspect NULL-extended rows, verify key cardinality, and separately count unmatched keys from both sides when appropriate.

13. Memory Review

Six-sentence chapter summary
  1. LEFT JOIN preserves every row from the left table.
  2. RIGHT JOIN preserves every row from the right table.
  3. FULL JOIN preserves unmatched rows from both sides.
  4. CROSS JOIN creates every possible row combination.
  5. A self join gives one table two or more logical roles through aliases.
  6. Join choice starts with deciding which unmatched rows must survive.
