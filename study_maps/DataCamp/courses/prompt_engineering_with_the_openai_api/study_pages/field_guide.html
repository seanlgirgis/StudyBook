2. Course Big Picture

Prompt engineering is the design of an input contract between an application and a language model. The contract defines behavior, supplies context, constrains output, and makes the result testable. Reliable systems do not trust fluent output alone: they validate structure, allowed values, source fidelity, safety, and business rules in deterministic code.

Business or user goal ↓ System behavior + trusted context ↓ User request + examples + constraints ↓ Model response ↓ Parse and validate ↓ Accept, retry, reject, or human review
Course punchline: A strong prompt narrows the model’s freedom, while application code verifies whether the answer is safe and usable.

3. Core Concepts

Message Roles

System messages define persistent behavior; user messages provide the current request; assistant messages can demonstrate desired behavior.

Examples and Shots

Zero-shot uses instructions only, one-shot demonstrates one pattern, and few-shot provides several representative examples.

Constraints and Structure

Define allowed labels, exact fields, word or sentence limits, output order, missing-value behavior, and fallback responses.

Task Decomposition

Use multi-step prompts when later work depends on earlier results; use concise reasoning formats when intermediate calculations aid review.

Grounded Business Output

Preserve source meaning during summaries, rewrites, translations, extraction, and code generation; do not let polished prose create new facts.

Chatbot State and Context

Combine a persistent system contract, recent messages, trusted context, and a validated structured state for stateful chat.

4. Core Syntax and Patterns

Bounded message request

messages = [
    Message(role="system", content=system_prompt),
    Message(role="user", content=user_prompt),
]
response = ai.get_response(messages=messages)

Separate lasting behavior from the current request. This makes the same chatbot contract reusable across many turns.

Fixed-schema extraction

prompt = f"""
Extract the ticket into valid JSON only.
Allowed categories: Billing, Technical, Account, General.
Use null for missing values.
Do not add extra keys.
```{ticket}```
"""

A fixed schema turns unstructured text into data that Python can parse and validate.

Structured rolling chat state

state = {
  "confirmed_facts": [],
  "recommended_actions": [],
  "completed_actions": [],
  "open_questions": []
}
# Model proposes updated_state; Python validates before storage.

Keep facts, advice, completed work, and unresolved questions separate to reduce memory drift.

5. Comparisons and Decision Rules

Prompt controls

Instructions, examples, delimiters, roles, context, output schemas, temperature, and fallback wording shape the model response.

Application controls

JSON parsing, exact-key checks, type checks, allowed-value validation, retries, logging, and human review determine whether the response is accepted.

Need Prompt pattern Main trap
Teach one format or label mapping One-shot or few-shot example Inconsistent examples teach inconsistent behavior.
Process unstructured business text Classification or extraction with fixed JSON schema Valid JSON can still contain incorrect facts.
Maintain chatbot continuity Recent messages plus compact structured state Repeated model-written summaries can drift without validation.

6. Common Mistakes

Using vague instructions Define the task, audience, source boundary, output format, limits, and acceptance rules.
Confusing examples with task steps Shots are demonstrations; steps are dependent stages inside the work.
Treating model output as validated data Parse and validate exact keys, types, allowed labels, null behavior, ranges, and source fidelity.
Letting conversation memory rewrite itself freely Separate confirmed facts from recommendations and completed actions, then validate proposed state updates before storage.

7. Interview Translation

How do you make an LLM output reliable for a data pipeline? I constrain the task with a fixed schema and allowed values, request machine-readable output, parse it, validate keys and types in deterministic code, and route failures to retry or review.
When would you use few-shot prompting? When instructions alone do not reliably convey the desired label mapping, style, structure, or edge-case behavior. I choose representative and consistent examples.
How would you design a stateful chatbot? I combine a system contract, a small window of recent messages, and compact structured state. The model proposes a state update, but application code validates it before storage.
What is the role of the system prompt? It defines persistent purpose, domain, tone, response rules, boundaries, fallback behavior, and small trusted context for the conversation.
