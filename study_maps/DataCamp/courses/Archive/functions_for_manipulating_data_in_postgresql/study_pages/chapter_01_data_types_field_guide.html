Section 4

Text Types

Chapter 1 starts with the core string choices: fixed-width CHAR, variable text with a length limit using VARCHAR, and flexible text using TEXT.

Type Length behavior Good for Main caution
CHAR(n) fixed/padded mindset legacy fixed codes padding can surprise
VARCHAR(n) variable with limit controlled labels limit must reflect business rule
TEXT flexible variable length descriptions and documents validation must come from other rules

CHAR(n)

Plain English: fixed-width text with a padded mindset.

Best use cases: product code, state code, or legacy fixed-length identifiers.

When not to use it: names, emails, descriptions, or any value with naturally variable length.

Generic syntax: column_name CHAR(4)

SELECT
  CAST('AB' AS CHAR(4)) AS fixed_code;
CREATE TABLE state_lookup (
  state_code CHAR(2)
);

Common trap: PostgreSQL pads to the declared width, so display and comparisons can feel surprising if you forget the fixed-width mindset.

Interview translation: use CHAR only when the business meaning is fixed-width, not just because the values are short today.

Memory line: CHAR = fixed/padded mindset.

VARCHAR(n)

Plain English: variable text with a rule-based maximum length.

Best use cases: short labels, customer names, controlled email fields, and input constrained by the business.

When not to use it: long descriptions or when you do not have a meaningful length rule.

Generic syntax: column_name VARCHAR(50)

CREATE TABLE customer_notes (
  short_label VARCHAR(50)
);
CREATE TABLE contacts (
  email_address VARCHAR(320)
);

Common trap: choosing a length limit because it looks neat instead of because the business actually requires it.

Interview translation: choose VARCHAR(n) when the maximum size is part of the business rule and worth enforcing at the schema layer.

Memory line: VARCHAR = variable text with optional limit.

TEXT

Plain English: flexible variable-length text for content that can grow.

Best use cases: descriptions, comments, notes, and document text.

When not to use it: fields that need a strict maximum length enforced by the database.

Generic syntax: column_name TEXT

CREATE TABLE documents (
  document_body TEXT
);
CREATE TABLE product_notes (
  note_body TEXT
);

Common trap: assuming flexibility means no validation is needed. You still may need application rules, trimming, or formatting checks.

Interview translation: TEXT is often the simplest choice when content length is genuinely open-ended.

Memory line: TEXT = flexible long text.

Product code and state code lean toward fixed or limited text. Customer names and emails usually fit VARCHAR when a meaningful limit exists. Descriptions, comments, and document text are natural TEXT cases.

Section 5

Numeric Types

The key numeric decision is whether you need whole numbers or exact decimals. That choice usually matters more than the exact numeric family name.

SELECT
  42::INTEGER AS item_count,
  19.95::NUMERIC(10,2) AS exact_price;
CREATE TABLE payments (
  payment_id BIGINT,
  amount NUMERIC(12,2)
);

Whole-number family

SMALLINT, INTEGER, and BIGINT are for counts, identifiers, quantities, and ages.

Exact decimal family

NUMERIC and DECIMAL are the go-to choices for exact money, exact percentages, and controlled decimal precision.

Approximate measurement

Floating-point types are acceptable for approximate scientific measurements or calculations where tiny binary rounding differences are acceptable.

Business value Suggested type
small countINTEGER
very large identifierBIGINT
exact moneyNUMERIC(p,s)
exact percentageNUMERIC(p,s)
approximate scientific measurementfloating-point type
Trap: Do not use an integer when fractional values matter. Do not assume floating-point values are exact money values.

Section 6

Date/Time Types

Core meanings

DATE = calendar day

TIME = clock time

TIMESTAMP = date and time without timezone interpretation

TIMESTAMPTZ = moment in time with timezone-aware storage/display behavior

INTERVAL = duration or relative offset

Common use cases

Birth date, invoice date, store opening time, local event timestamp, global event timestamp, allowed rental duration, elapsed time, and future deadline calculations.

SELECT
  CURRENT_DATE AS today,
  CURRENT_TIME AS current_clock,
  CURRENT_TIMESTAMP AS current_moment,
  INTERVAL '5 days' AS five_day_duration;
SELECT
  rental_date + INTERVAL '5 days' AS expected_return_date;
Need Type
calendar day onlyDATE
time of day onlyTIME
local date and timeTIMESTAMP
absolute moment across time zonesTIMESTAMPTZ
duration or offsetINTERVAL

Trap: date-only vs timestamp

If time detail matters, avoid converting to DATE too early.

Trap: timezone assumptions

When events cross regions, think in terms of moments, not just local clock labels.

Trap: interval confusion

An INTERVAL is not the same thing as a stored timestamp value.

Section 7

Array Types

PostgreSQL arrays let one column hold multiple simple values. They display like ordered lists, and indexing starts at 1, not 0.

SELECT ARRAY['sql', 'analytics', 'postgres'] AS tags;
SELECT
  favorite_tags[1] AS first_tag,
  favorite_tags[2] AS second_tag
FROM lab_customers;
SELECT *
FROM lab_customers
WHERE 'sql' = ANY(favorite_tags);
SELECT *
FROM lab_customers
WHERE favorite_tags @> ARRAY['sql'];
SELECT *
FROM lab_customers
WHERE favorite_tags @> ARRAY['sql', 'postgres'];
SELECT
  favorite_tags,
  CARDINALITY(favorite_tags) AS tag_count
FROM lab_customers;
SELECT
  first_name,
  favorite_tags,
  favorite_tags[1] AS primary_interest,
  CARDINALITY(favorite_tags) AS interest_count,
  'sql' = ANY(favorite_tags) AS interested_in_sql
FROM lab_customers
ORDER BY first_name;
Need Pattern
first itemarray_col[1]
one searched value appears'value' = ANY(array_col)
array contains one requested valuearray_col @> ARRAY['value']
array contains all requested valuesarray_col @> ARRAY['a','b']
count elementsCARDINALITY(array_col)

Common array mistakes

  • Using [0] instead of [1]
  • Confusing ANY() and @>
  • Forgetting the right side of @> must be an array
  • Using arrays where a relational child table is more appropriate

How arrays help

They are handy when the list is small, simple, and usually retrieved with the parent row. They are less ideal when each element needs its own attributes, joins, or lifecycle.

Use an array when

  • the list is small
  • values are simple
  • values usually travel together
  • complex joins are not required

Prefer a child table when

  • values need their own attributes
  • values change independently
  • referential integrity matters
  • many-to-many relationships are needed
  • detailed analytics are required

Section 8

Metadata Discovery

Before guessing a type, inspect the database. PostgreSQL gives you a reliable map through information_schema.columns.

Find schema → inspect tables → inspect columns → inspect data_type → inspect udt_name when PostgreSQL-specific detail matters 
SELECT
  table_schema,
  table_name,
  column_name,
  data_type,
  udt_name
FROM information_schema.columns
WHERE table_name = 'lab_rentals'
ORDER BY ordinal_position;
SELECT
  table_name,
  column_name,
  data_type,
  udt_name
FROM information_schema.columns
WHERE table_schema = 'course06_functions_lab'
ORDER BY table_name, ordinal_position;
SELECT
  table_schema,
  table_name,
  column_name,
  data_type,
  udt_name
FROM information_schema.columns
WHERE data_type = 'ARRAY'
ORDER BY table_schema, table_name, ordinal_position;

table_schema

Critical for finding tables outside public, especially in course or app-specific schemas.

data_type

Human-readable category such as integer, text, or ARRAY.

udt_name

Shows PostgreSQL internal or base type detail, which helps when data_type is broad.

Common trap: filtering only public can hide the real table.

Section 9

User-Defined Types

A user-defined type is registered in PostgreSQL and can be used anywhere PostgreSQL expects a type name. An enum is a user-defined type containing a controlled list of allowed values.

Video lesson coverage

CREATE TYPE registers the type, pg_type shows the catalog entry, and information_schema.columns uses data_type = 'USER-DEFINED' plus udt_name to reveal the actual PostgreSQL type name on a column.

CREATE TYPE dayofweek AS ENUM (
  'Monday',
  'Tuesday',
  'Wednesday',
  'Thursday',
  'Friday',
  'Saturday',
  'Sunday'
);
The new type is named dayofweek.
A column using this type may contain only one of the values listed in the enum definition. 
CREATE TABLE class_schedule (
  class_id integer,
  class_day dayofweek
);
INSERT INTO class_schedule (
  class_id,
  class_day
)
VALUES (
  1,
  'Monday'
);

An attempt to store a value that is not in the enum list, such as 'Holiday', will fail.

When an enum is useful

  • stable status values
  • days of the week
  • controlled categories
  • values that should be validated by the database
  • values that are unlikely to change often

Important caution

"Never going to change" is an idealized teaching phrase.

In real systems, enum values can change, but changing them requires schema work and careful deployment.

Need Enum Lookup table
small stable liststrong choicealso possible
values change oftenless flexiblebetter choice
values need descriptions or attributesweak choicebetter choice
foreign-key relationships requirednot idealbetter choice
database-level value restrictionbuilt inprovided through foreign key
application-readable controlled vocabularyusefuluseful

Memory line: Enum = controlled type value
Lookup table = controlled relational entity

Inspecting user-defined types with pg_type

pg_type is a PostgreSQL system catalog containing built-in and user-defined type information.

SELECT
  typname,
  typcategory
FROM pg_type
WHERE typname = 'dayofweek';

typname = the PostgreSQL type name

typcategory = a one-character category code used internally by PostgreSQL

E = enum category

Find enum types

SELECT
  typname,
  typcategory
FROM pg_type
WHERE typcategory = 'E'
ORDER BY typname;

This finds enum types visible in the current database catalogs.

Inspect a known user-defined column

SELECT
  table_schema,
  table_name,
  column_name,
  data_type,
  udt_name
FROM information_schema.columns
WHERE table_name = 'film'
  AND column_name = 'rating';

data_type = USER-DEFINED

udt_name = mpaa_rating

data_type tells us that the column uses a custom PostgreSQL type.

udt_name tells us the actual underlying user-defined type name.

Find user-defined columns broadly

SELECT
  table_schema,
  table_name,
  column_name,
  data_type,
  udt_name
FROM information_schema.columns
WHERE data_type = 'USER-DEFINED'
ORDER BY
  table_schema,
  table_name,
  ordinal_position;

Section 10

Type Selection Guide

Ask these questions first

  • Is the value text, numeric, date/time, or multi-valued?
  • Does exact precision matter?
  • Does time zone matter?
  • Does the value need a length constraint?
  • Does the value need a controlled vocabulary?
  • Will the multi-valued data need joins or its own attributes?

One important habit

Phone numbers are usually text, not numeric values. They are identifiers with formatting, leading zeros, country codes, and symbols, not values you calculate with.

Section 11

Combined Examples

Example 1: Customer data shape

Business question: What does customer tag data look like at the row level?

SELECT
  customer_id,
  first_name,
  last_name,
  favorite_tags,
  favorite_tags[1] AS primary_tag,
  CARDINALITY(favorite_tags) AS tag_count
FROM lab_customers;

What to notice: arrays can be shown, indexed, and counted in the same query.

Likely mistake: trying favorite_tags[0].

Example 2: Inspect before querying

Business question: What are the real column types before I write logic?

SELECT
  column_name,
  data_type,
  udt_name
FROM information_schema.columns
WHERE table_schema = 'course06_functions_lab'
  AND table_name = 'lab_customers'
ORDER BY ordinal_position;

What to notice: table_schema, data_type, and udt_name together prevent blind guessing.

Likely mistake: filtering only public and missing the table.

Example 3: Find SQL-oriented customers

Business question: Which customers are interested in SQL?

SELECT
  customer_id,
  first_name,
  favorite_tags
FROM lab_customers
WHERE 'sql' = ANY(favorite_tags)
ORDER BY customer_id;

What to notice: ANY checks whether one searched value appears in the array.

Likely mistake: confusing this with @> containment syntax.

Example 4: Type-safe date/time calculation

Business question: What is the expected return date if rentals last three days?

SELECT
  rental_id,
  rental_date,
  rental_date + INTERVAL '3 days' AS expected_return_date
FROM lab_rentals;

What to notice: INTERVAL keeps the calculation in the date/time family.

Likely mistake: converting to DATE before the calculation when time still matters.

Section 12

Common Mistakes

Mistake Why it happens Correction Memory line
Assuming arrays start at 0 Many programming languages train that reflex. Use [1] for the first PostgreSQL array element. PostgreSQL arrays start at 1.
Filtering metadata only to public People expect every table to live there. Inspect table_schema and use the real schema name. table_schema matters.
Treating phone numbers as numeric They look number-like at a glance. Store them as text because formatting and leading zeros matter. Phone numbers are identifiers, not arithmetic.
Using integer for money Whole-number types feel simple and familiar. Use NUMERIC(p,s) when cents matter. Money is usually exact decimal.
Using floating point for exact money Decimals look natural in floating-point syntax. Use NUMERIC for exact currency values. Float is approximate, not exact money.
Using CHAR without understanding padding Fixed-width behavior is easy to underestimate. Choose VARCHAR unless fixed-width meaning is intentional. CHAR = fixed/padded mindset.
Casting timestamp to date too early People want a neat display before finishing logic. Keep full timestamp detail until the calculation is complete. Do not drop time detail before you are done.
Confusing TIMESTAMP with INTERVAL Both are part of date/time work. TIMESTAMP is a moment; INTERVAL is a duration or offset. Moment versus duration.
Using arrays for complex relational data Arrays feel faster than designing child tables. Use a child table when elements need joins, attributes, or integrity rules. Simple list: array. Relational list: child table.
Ignoring timezone needs Local development can hide global reality. Use TIMESTAMPTZ when you care about the absolute moment across regions. Cross-region events need moment-aware thinking.
Relying only on file or UI labels instead of inspecting metadata Names can sound trustworthy. Query information_schema.columns before assuming types. Inspect first, guess second.
Assuming data_type and udt_name are identical Both appear in the same metadata result. Use data_type for broad category and udt_name for PostgreSQL-specific detail. Broad label versus internal detail.
Assuming USER-DEFINED is the actual type name The broad metadata label looks descriptive enough. Check udt_name to see the real PostgreSQL type such as mpaa_rating. USER-DEFINED means keep digging.
Assuming every controlled list should be an enum Enums look tidy and strongly typed. Use a lookup table when values need attributes, ordering, or frequent change. Stable labels = enum; relational values = table.
Assuming enums can never change People hear "stable list" and infer total immutability. Enums can change, but schema changes need care and should not replace flexible lookup-table design. Possible to change, expensive to treat casually.
Querying only information_schema.columns.data_type The first type column looks complete. Inspect udt_name too when PostgreSQL-specific type detail matters. Broad label plus internal name.
Assuming pg_type contains only custom types The catalog name sounds like a special-purpose list. Remember it includes built-in and user-defined PostgreSQL types. Catalogs usually contain the whole family.
Assuming typcategory = 'E' is the enum value itself Single-letter codes can look like data values. Treat it as a category marker that means "enum type." 'E' = enum category, not enum label.

Section 13

Interview Q&A

How do you discover a PostgreSQL column type?

Query information_schema.columns and inspect table_schema, column_name, data_type, and udt_name.

What is the difference between VARCHAR and TEXT?

VARCHAR(n) adds a length rule. TEXT is flexible when no meaningful limit is needed.

When would you use NUMERIC instead of INTEGER?

Use NUMERIC when exact decimal values matter, such as money or exact percentages.

Why should money normally use NUMERIC?

Because money needs exact decimal precision, and floating point can introduce approximation errors.

What is the difference between DATE and TIMESTAMP?

DATE stores the day only. TIMESTAMP stores both date and time.

What is INTERVAL?

An INTERVAL is a duration or offset used in date/time calculations.

What is a PostgreSQL array?

It is a column value that can hold multiple ordered elements of the same base type.

What is the array indexing trap?

People expect zero-based indexing, but PostgreSQL arrays start at 1.

What is the difference between ANY and @>?

ANY checks whether one searched value appears. @> checks whether the left array contains the requested array.

When would you avoid an array?

Avoid arrays when elements need joins, their own attributes, referential integrity, or many-to-many analytics.

What does udt_name tell you?

It gives PostgreSQL-specific internal or base type detail beyond the broad data_type label.

What is a PostgreSQL user-defined type?

It is a type you register in PostgreSQL so it can be reused anywhere a type name is expected, such as a custom enum.

What is an enum?

An enum is a type with a controlled list of allowed labels, such as days of the week or a stable status list.

How do you create an enum?

Use CREATE TYPE type_name AS ENUM (...) and then assign that type to a column.

How do you inspect a type through pg_type?

Query pg_type and inspect fields like typname and typcategory.

What does typname mean?

It is the PostgreSQL type name stored in the system catalog.

What does typcategory = 'E' mean?

It means the type belongs to PostgreSQL's enum category.

What does data_type = 'USER-DEFINED' mean?

It means the broad metadata label is not enough and you should inspect udt_name for the actual PostgreSQL type name.

When is an enum a good choice?

When the allowed labels are small, stable, and do not need extra relational attributes.

When might a lookup table be better than an enum?

When values change often or need descriptions, ordering, flags, or other relational attributes.
